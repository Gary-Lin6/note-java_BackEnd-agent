MySQL中的锁，按照锁的粒度分，分为以下三类：​
1.全局锁：锁定数据库中的所有表​
2.表级锁：每次操作锁住整张表​
3.行级锁：每次操作锁住对应的行数据
# 一.全局锁
全局锁就是对整个数据库实例加锁，加锁后整个实例就处于只读状态，后续的DML的写语句，DDL语句，已经更新操作的事务提交语句都将被阻塞。​

其典型的使用场景是做全库的逻辑备份，对所有的表进行锁定，从而获取一致性视图，保证数据的完整性。

>[!info] 如何加锁解锁

```mysql
#加锁
flush tables with read lock;

#解锁
unlock tables;
```

>[!info] 全局锁的缺点

1.如果在主库上备份，那么在备份期间都不能执行更新，业务基本上就得停摆​
2.如果在从库上备份，那么在备份期间从库不能执行主库同步过来的二进制日志(binlog)，会导致主从延迟

>[!info] 解决方案

InnoDB引擎支持可重复读隔离级别。只用在备份前开启事务，并创建一个readview，接下来根据这个readview来读取相应历史版本即可数据即可。外界的增删改操作不会影响备份表时的读操作。
具体：mysqldump时加上--single-transaction

# 二.表级锁
每次操作锁住整张表。锁定粒度大，发生锁的冲突的概率最高，并发度最低。应用在MyISAM、InnoDB、BDB等存储引擎中​
对于表级锁，主要分为以下四类：​
1.表锁​
2.元数据锁（meta data lock，MDL）​
3.意向锁
4.AUTO-INC锁
## 1.表锁
对于表锁，分为两类：​
1.表共享读锁（read lock）：
- 当前线程：可以读，不能写该表（报错），不能访问别的表
- 其他线程：可以读，不能写该表（阻塞）
2.表独占写锁（write lock）：
- 当前线程：可以读和写
- 其他线程：不可以度和写（阻塞）
```mysql
#加锁
lock tables 表名... read|write;

#释放锁
unlock tables;
```

## 2.元数据锁（MDL）
我们不需要显示的使用 MDL，因为当我们对数据库表进行操作时，会自动给这个表加上 MDL：

- 对一张表进行 CRUD 操作时，加的是 MDL 读锁；
  细化：
	- 查：共享读锁
	- 增删改：共享写锁
	共享读锁和共享写锁不互斥，所以也可以把他们归一类
- 对一张表做结构变更操作的时候，加的是 MDL 写锁；
MDL 是为了保证当用户对表执行 CRUD 操作时，防止其他线程对这个表结构做了变更。

当有线程在执行 select 语句（ 加 MDL 读锁）的期间，如果有其他线程要更改该表的结构（ 申请 MDL 写锁），那么将会被阻塞，直到执行完 select 语句（ 释放 MDL 读锁）。

反之，当有线程对表结构进行变更（ 加 MDL 写锁）的期间，如果有其他线程执行了 CRUD 操作（ 申请 MDL 读锁），那么就会被阻塞，直到表结构变更完成（ 释放 MDL 写锁）。

除了读读不互斥外，读写，写写均互斥。

>[!info] 阻塞现象

看一个例子：
首先，线程 A 先启用了事务（但是一直不提交），然后执行一条 select 语句，此时就先对该表加上 MDL 读锁；

然后，线程 B 也执行了同样的 select 语句，此时并不会阻塞，因为「读读」并不冲突；

接着，线程 C 修改了表字段，此时由于线程 A 的事务并没有提交，也就是 MDL 读锁还在占用着，这时线程 C 就无法申请到 MDL 写锁，就会被阻塞，

那么在线程 C 阻塞后，**后续有对该表的 select 语句，就都会被阻塞**，如果此时有大量该表的 select 语句的请求到来，就会有大量的线程被阻塞住，这时数据库的线程很快就会爆满了。

**为什么后面的select会被阻塞？不是读读不互斥吗？**
这是因为申请 MDL 锁的操作会形成一个队列，队列中写锁获取优先级高于读锁，一旦出现 MDL 写锁等待，会阻塞后续该表的所有 CRUD 操作。

## 3.意向锁

>[!info] 为什么要有意向锁

没有意向锁时，因为还有行锁，所以在加表锁前，要先逐行检查有没有互斥的行锁，性能比较低。有了意向锁，在加锁前，只用检查该表的意向锁是什么类型的就能快速判断能不能获取到锁。
所以，意向锁的目的是为了快速判断表里是否有记录被加锁。

>[!info] 意向锁是怎么加锁的？

在对记录（行）加锁时，先给表加意向锁，再给记录加锁。
- 给行加共享锁，先给表加意向共享锁，再给行加共享锁
- 给行加独占锁，先给表加意向独占锁，再给行加独占锁。

注意：共享锁（行锁）与共享表锁（表共享读锁）（表锁），
独占锁（行锁）与独占行锁（表独占写锁）（表锁）
的区别。

>[!info] 意向锁的互斥情况。

意向锁间不互斥，意向锁与表锁可能互斥（读读兼容，其他互斥）
**为什么意向锁间不互斥**
因为意向锁代表的是表中的某一行，表里可能有很多行，如果意向锁可能互斥，那么说明行锁间有影响。所以意向锁间不能互斥

意向锁与表锁可能互斥原因即为什么要有意向锁。

## 4.AUTO-INC锁

>[!info] 为什么要有AUTO-INC锁

因为要实现逐渐auto-increment功能，如果没有AUTO-INC锁，那么同时插入两条数据，可能会导致在前面行的主键比后面行小（也就是主键不自增）。
AUTO-INC刚开始设计时，在插入数据时会加一个表级的AUTO-INC锁，来阻塞要插入的语句。
但如果插入插入语句很多，就会导致性能下降。于是AUTO-INC设计了三个粒度

>[!info] 三个粒度

InnoDB 存储引擎提供了个 innodb_autoinc_lock_mode 的系统变量，是用来控制选择用 AUTO-INC 锁，还是轻量级的锁。

当 innodb_autoinc_lock_mode = 0，就采用 AUTO-INC 锁，语句执行结束后才释放锁；
当 innodb_autoinc_lock_mode = 2，就采用轻量级锁，申请自增主键后就释放锁，并不需要等语句执行后才释放。
当 innodb_autoinc_lock_mode = 1：
普通 insert 语句，自增锁在申请之后就马上释放；
类似 insert … select 这样的批量插入数据的语句，自增锁还是要等语句结束后才被释放；

但可能会导致主从不一致，具体见[轻量级锁带来的问题及解决方案](https://xiaolincoding.com/mysql/lock/mysql_lock.html#auto-inc-%E9%94%81)
解决方案是binlog选择row形式记录

# 三.行级锁
行级锁，每次操作**锁住对应的行数据**。锁定粒度最小，发生锁冲突的概率最低，并发度最高。应用在InnoDB存储引擎中

行级锁主要分为三类：

1. 行锁(Record Lock)：锁定单个行记录的锁，防止其他事务对此行进行update和delete。在RC（读提交）、RR（可重复读）隔离级别下都支持
2. 间隙锁(GapLock)：锁定索引记录间隙(不含该记录)，确保索引记录间隙不变，防止其他事务在这个间隙进行insert，产生幻读。在RR（可重复读）隔离级别下都支持
3. 临键锁(Next-Key Lock)：行锁和间隙锁组合，同时锁住数据，并锁住数据前面的间隙Gap。在RR（可重复读）隔离级别下支持
4. 插入意向锁
## 1.行锁
Record Lock 称为记录锁，锁住的是一行记录。而且记录锁是有 S 锁和 X 锁之分：​
1.共享锁(S)：允许一个事务去读一行，阻止其他事务获得相同数据集的排它锁。​
	◦当前客户端和其他客户端都能读，当前客户端不能写，其他客户端写被阻塞​
2.排他锁(X)：允许获取排他锁的事务更新数据，阻止其他事务获得相同数据集的共享锁和排他锁。​
	◦当前客户端可以读和写，其他客户端的读和写会被阻塞
有点像表锁，只不过锁住的是一行而不是整张表

>[!info] 如何加锁，释放锁

| SQL                          | 行锁类型  | 说明                               |
| ---------------------------- | ----- | -------------------------------- |
| insert...，update...，delete … | 排他锁   | 自动加锁                             |
| select...（正常）                | 不加任何锁 |                                  |
| select … lock in share mode  | 共享锁   | 需要手动select之后加上lock in share mode |
| select … for update          | 排他锁   | 需要手动在select之后for update          |

释放锁：事务提交自动释放

## 2.Gap Lock
Gap Lock 称为间隙锁，存在于可重复读隔离级别和串行化隔离级别，目的是为了解决可重复读隔离级别下幻读的现象。

假设，表中有一个范围 id 为（3，5）间隙锁，那么其他事务就无法插入 id = 4 这条记录了，这样就有效的防止幻读现象的发生。
![[Pasted image 20260428203710.png]]
间隙锁虽然存在 X 型间隙锁和 S 型间隙锁，但是并没有什么区别，间隙锁之间是兼容的，即两个事务可以同时持有包含共同间隙范围的间隙锁，并不存在互斥关系，因为间隙锁的目的是防止插入幻影记录而提出的。

## 3.Next-Key Lock
Next-Key Lock 称为临键锁，是 Record Lock + Gap Lock 的组合，锁定一个范围，并且锁定记录本身。

假设，表中有一个范围 id 为（3，5] 的 next-key lock，那么其他事务即不能插入 id = 4 记录，也不能修改 id = 5 这条记录。
![[Pasted image 20260428203805.png]]
所以，next-key lock 即能保护该记录，又能阻止其他事务将新纪录插入到被保护记录前面的间隙中。

next-key lock 是包含间隙锁+记录锁的，如果一个事务获取了 X 型的 next-key lock，那么另外一个事务在获取相同范围的 X 型的 next-key lock 时，是会被阻塞的。

比如，一个事务持有了范围为 (1, 10] 的 X 型的 next-key lock，那么另外一个事务在获取相同范围的 X 型的 next-key lock 时，就会被阻塞。

虽然相同范围的间隙锁是多个事务相互兼容的，但对于记录锁，我们是要考虑 X 型与 S 型关系，X 型的记录锁与 X 型的记录锁是冲突的。

## 4.插入意向锁
一个事务在插入一条记录的时候，需要判断插入位置是否已被其他事务加了间隙锁（next-key lock 也包含间隙锁）。

如果有的话，插入操作就会发生阻塞，直到拥有间隙锁的那个事务提交为止（释放间隙锁的时刻），在此期间会生成一个插入意向锁，表明有事务想在某个区间插入新记录，但是现在处于等待状态。
举个例子，假设事务 A 已经对表加了一个范围 id 为（3，5）间隙锁。
![[Pasted image 20260428211045.png]]
当事务 A 还没提交的时候，事务 B 向该表插入一条 id = 4 的新记录，这时会判断到插入的位置已经被事务 A 加了间隙锁，于是事物 B 会生成一个插入意向锁，然后将锁的状态设置为等待状态<span style="color:pink;">（PS：MySQL 加锁时，是先生成锁结构，然后设置锁的状态，如果锁状态是等待状态，并不是意味着事务成功获取到了锁，只有当锁状态为正常状态时，才代表事务成功获取到了锁）</span>，此时事务 B 就会发生阻塞，直到事务 A 提交了事务。

插入意向锁是特殊的间隙锁：间隙锁锁住一个区间，插入意向锁锁住的就是一个点

## 5.MySQL是怎么加行级锁的？
首先要清楚，要解决读写冲突，加行锁就够了，其实没必要用间隙锁和邻键锁。但innodb就是实现了这两把锁，为什么？
其实是要在可重复度的条件下，尽可能避免幻读。
什么是幻读：前后查询某一行，某一行（存在性不同：从存在到不存在，或从不存在到存在）或者查询某几行，新增或减少了几行。
怎么解决幻读：避免幻读就是避免结果集某一条记录被其他事务删除，或者有其他事务插入了一条新记录
详见[[1.MySQL事务#3.幻读]]

其次要清楚：锁加在哪里？
锁其实是加在索引上的，索引具体是什么：详见[[5.MySQL索引]]


最后我们详细了解下加行锁的规则。
我们可以认为，mysql加行级锁，一开始都是加next-key lock，但如果行锁，或间隙锁就能解决幻读，那么next-key lock退化成行锁或间隙锁。

分为以下4种情况
以下的查询指：where 后面的条件
### 5.1唯一索引等值查询
#### 5.1.1记录存在
退化成行锁

>[!info] 为什么退化成行锁就能避免幻读

1.无法插入：由于主键具有唯一性，所以其他事务插入 id = 1 的时候，会因为主键冲突，导致无法插入 id = 1 的新记录。
2.无法删除：由于对 id = 1 加了记录锁，**其他事务无法删除该记录**，

因此用行锁就能保证避免幻读

#### 5.1.2记录不存在
查询k，k不存在。假设i，j存在，且i<k<j.
那么会退化成间隙锁，锁住（i，j）
特别的，不存在j或不存在i（即k比最大索引大/最小索引小），锁住（j，∞）/（-∞，i）

>[!info] 为什么退化成间隙锁就能避免幻读

1.不能退化成行锁，因为行锁是针对索引的，索引都不存在，自然不能加锁。
2.用间隙锁就能够防止幻读，不用给j单独加锁。因为我们查询的是id=k这一行，关心的是k这一行前后的存在情况。只要k这一行前后存在情况一致，就避免了幻读，其它行的变化我们并不关心。

### 5.2唯一索引范围查询
例如查询id>k,假设i，j存在，且i<k<j.
其实我们自己就能推导出来，应该在哪加什么锁：
为了防止前后查询新增或减少某几行。那么j后面通通都要加next-key lock。
那么(i,j)范围呢？
很显然不能加行锁，因为k不存在，而且加了，（k，j）也无法保证？
显然不能加间隙锁，因为加了j没加锁，j可能被删除。
综上只能加邻键锁。

再假设id>=k,其实可以划分成，id== k&&id>k加锁结果的并集。前面提过id == k退化成间隙锁，但是id>k在（i，j）加的是邻键锁，所以并集还是和上面一样。

最后来看下k== i的情况。
id>k时，一样的，j后面通通都要加next-key lock。
（i，j）范围其实还是加next key lock，因为我们不用关心i是否有变化，因为我们关心的是id>k的情况，i变不变，对结果集没影响。

id>=k时，划分成，id== k&&id>k加锁结果的并集。
所以还要再加个 id=i的行锁。

以上是大于情况，小于类似。

### 5.3非唯一索引等值查询
以where name=k为例（name为二级索引）
非唯一索引进行加锁时，不仅要对非唯一索引加锁，还得给对应的主键索引加锁。因为非唯一索引查询规则是先查二级索引，再根据二级索引上的主键，回表查询主键索引。因此，如果不给主键索引加锁的话，可能不走非唯一索引的插入删除语句依旧会更新成功，导致幻读。

#### 5.3.1记录存在
因为非唯一索引值可能重复，所以会扫描第一个直到最后一个不满足条件的索引，加锁规则如下：
```
//二级索引
上一个不满足条件索引
		|         ------|
第一个满足条件索引：       |
		|               |
第二个满足条件索引		    |
		|               |  next key lock
	   ...              |
		|               | 
最后一个满足条件索引：-----|
		|  <---------- 间隙锁       
第一个不满足条件索引：


//每个对应的主键：行锁
```

>[!info] 为什么这些区间要加锁

如果不加间隙锁，那么可以再插入name=k，而其他值不同的数据(因为二级索引可以重复)，造成幻读。
如果不加行锁，那么可以删除某条name=k的数据，造成幻读。
而间隙锁+行锁即为next key lock

>[!info] 为什么最后一处退化成间隙锁

因为对于下一个索引而言，它的增加和删除对于此时查询的结果级不造成影响。所以不用加行锁。
next key lock也就退化成了间隙锁。

>[!info] 为什么每条索引对应的主键索引也要加行锁

因为如果主键索引不加锁的话，那么其他不经过该索引的修改语句可以删除对应主键的数据，造成幻读。
**为什么主键间不加间隙锁？**
没必要，我们防止的是name=k这个区间的数据不会增加或删除，
如果要想增加，那只能是insert ...where name =k，会经过二级索引被阻塞。
（你找不到一个语句能不带name且能插到name=k这个区间吧）
如果要删除，一种方法是delect ... where name =k，一种是指定删除对应主键，再一种是通过别的索引找到主键删除。第一种二级索引加了锁，删不掉。而主键加了行锁，也删不掉。
主键如果要加间隙锁，锁住的是主键间的间隙，对于name=k这个区间根本没影响，所以只用加行锁即可。

#### 5.3.2记录不存在
name=k，存在i，j。i<k< j
会在应该插入的地方(i,j)加间隙锁。主键索引不加锁
就和唯一索引等值查询记录不存在理由相同。

>[!info] 但是有时候，我们插入name=i或name=j的语句会被阻塞，why？

其实原因很简单，你插入到上个索引后方，和下个索引的前方了
```
|           间隙锁         |              
name=i------------------name=j
 |          |      
 |          |             j同理
 插入到这  插入到这
 ok         阻塞
```


### 5.4 非唯一索引范围查询
不会退化，对应主键加行锁
其实在唯一索引范围查询也分析了，唯一索引只有查存在i=k，id>=k的情况，i前面会退化成i的行锁，而后面均是邻键锁。
那么非唯一索引其他情况和唯一索引相同，对于上述i=k，name>=k的情况，也不会退化。
因为如果退化成行锁，前面也是可以插入name=k的数据的。那么就会造成幻读，所以前面也得锁住。

## 5.5没有加索引的查询
相当于给每一行加next key lock，也就是加了表锁。
