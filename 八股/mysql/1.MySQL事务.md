**事务是什么？**
事务是一组操作的集合，事务会把所有操作作为一个整体一起向系统提交或撤销操作请求，即这些操作要么同时成功，要么同时失败。

**为什么要有事务？**
如果没有事务，那么一组操作如转账，正常：我转你100，分为两步，我-100，你+100。但可能我-100了，结果中间出错了，导致你没有+100。
有了事务，我们就可以保证这组操作是原子的，要么同时成功，要么同时失败。
但除此之外，事务还有别的好处。

# 一.事务的四大特性（ACID）
- 原子性(**A**tomicity)：事务是不可分割的最小操作单元，要么全部成功，要么全部失败
- 一致性(**C**onsistency)：是指事务操作前和操作后，数据满足完整性约束，数据库保持一致性状态。
		比如，用户 A 和用户 B 在银行分别有 800 元和 600 元，总共 1400 元，用户 A 给用户 B 转账 200 元，分为两个步骤，从 A 的账户扣除 200 元和对 B 的账户增加 200 元。一致性就是要求上述步骤操作后，最后的结果是用户 A 还有 600 元，用户 B 有 800 元，总共 1400 元，而不会出现用户 A 扣除了 200 元，但用户 B 未增加的情况（该情况，用户 A 和 B 均为 600 元，总共 1200 元）。
- 隔离性(**I**solation)：数据库系统提供的隔离机制，保证事务在不受外部并发操作影响的独立环境下运行
- 持久性(**D**urability)：事务一旦提交或回滚，它对数据库中的数据的改变就是永久的


>[!info] InnoDB 引擎通过什么技术来保证事务的这四个特性的呢？

**原子性**是通过 undo log（回滚日志） 来保证的；
**持久性**是通过 redo log （重做日志）来保证的；
具体原理见[[2.MySQL日志]]

**隔离性**是通过 MVCC（多版本并发控制） 或锁机制来保证的；
[[3.MySQL锁]]

**一致性**则是通过持久性+原子性+隔离性来保证；

# 二.并发事务引起的问题
事务有这么多优点，那是不是就没有别的问题了呢？
对于单线程而言，事务已经很完美了，但对于允许多客户端的mysql而言，并发事务可能会引起以下问题

| 问题    | 描述                                          |
| ----- | ------------------------------------------- |
| 脏读    | 一个事务读到另一个事务还没提交的数据                          |
| 不可重复读 | 一个事务先后读取同一条记录，但两次读取的数据不同                    |
| 幻读    | 一个事务按照条件查询数据时，没有对应的数据行，但是再插入数据时，又发现这行数据已经存在 |

这三个现象的严重性排序如下：

## 1.脏读
<span style="color:blue;">如果一个事务「读到」了另一个「未提交事务修改过的数据」，就意味着发生了「脏读」现象。</span>

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库中读取小林的余额数据，然后再执行更新操作，如果此时事务 A 还没有提交事务，而此时正好事务 B 也从数据库中读取小林的余额数据，那么事务 B 读取到的余额数据是刚才事务 A 更新后的数据，即使没有提交事务。
![[Pasted image 20260425220345.png]]

因为事务 A 是还没提交事务的，也就是它随时可能发生回滚操作，如果在上面这种情况事务 A 发生了回滚，那么事务 B 刚才得到的数据就是过期的数据，这种现象就被称为脏读。

## 2.不可重复读
<span style="color:blue;">在一个事务内多次读取同一个数据，如果出现前后两次读到的数据不一样的情况，就意味着发生了「不可重复读」现象。</span>

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库中读取小林的余额数据，然后继续执行代码逻辑处理，在这过程中如果事务 B 更新了这条数据，并提交了事务，那么当事务 A 再次读取该数据时，就会发现前后两次读到的数据是不一致的，这种现象就被称为不可重复读。
![[Pasted image 20260425220449.png]]
注意和脏读区别：
脏读是A提交事务前更新的数据被B读取了。结果A事务回滚了，导致数据错误。
不可重复读是A在一个事务内前后两次读取，因为B事件更改并提交事务导致的不同

## 3.幻读
<span style="color:blue;">在一个事务内多次查询某个符合查询条件的「记录数量」，如果出现前后两次查询到的记录数量不一样的情况，就意味着发生了「幻读」现象。</span>

举个栗子。

假设有 A 和 B 这两个事务同时在处理，事务 A 先开始从数据库查询账户余额大于 100 万的记录，发现共有 5 条，然后事务 B 也按相同的搜索条件也是查询出了 5 条记录。
![[Pasted image 20260425220853.png]]
接下来，事务 A 插入了一条余额超过 100 万的账号，并提交了事务，此时数据库超过 100 万余额的账号个数就变为 6。

然后事务 B 再次查询账户余额大于 100 万的记录，此时查询到的记录数量有 6 条，发现和前一次读到的记录数量不一样了，就感觉发生了幻觉一样，这种现象就被称为幻读。


# 三.事务隔离级别
SQL 标准提出了四种隔离级别来规避这些现象，隔离级别越高，性能效率就越低，这四个隔离级别如下：

<span style="color:blue;">读未提交（read uncommitted）</span>，指一个事务还没提交时，它做的变更就能被其他事务看到；
<span style="color:blue;">读提交（read committed）</span>，指一个事务提交之后，它做的变更才能被其他事务看到；
<span style="color:blue;">可重复读（repeatable read）</span>，指一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的，MySQL InnoDB 引擎的默认隔离级别；
<span style="color:blue;">串行化（serializable ）</span>；会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行；

## 1.实现原理
并发事务引发的问题，归根到底是读写冲突问题。因此事务隔离级别就是使用不同策略来应对读写冲突。
1.读未提交：不做任何处理
2.读已提交：使用MVCC，在每次select时生成一个readview
3.可重复读：使用MVCC,对于每个事务只有第一次select时才生成readview，后续同一事务的select复用第一次select产生的readview。
对于MVCC详见：[[2.MySQL日志#2.MVCC实现原理]]
4.串行化：表锁
对于锁详见：[[3.MySQL锁]]

## 2.可重复为什么没完全避免幻读

>[!info] 可重复可在很大程度上避免幻读，为什么？

对于快照读：使用第一次快照读生成的readview，避免了前后两次快照读查询结果集不一致
对于当前读：使用next key lock避免幻读。

>[!info] 听起来好像已经解决了幻读，为什么还有幻读出现呢？

虽然说前后的readview是一样的，但是更新语句的undolog上的trx_id是自己，那么就能查询到这条数据，导致幻读。

再举一个例子：
除了上面这一种场景会发生幻读现象之外，还有下面这个场景也会发生幻读现象。

T1 时刻：事务 A 先执行「快照读语句」：select * from t_test where id > 100 得到了 3 条记录。
T2 时刻：事务 B 往插入一个 id= 200 的记录并提交；
T3 时刻：事务 A 再执行「当前读语句」 select * from t_test where id > 100 for update 就会得到 4 条记录，此时也发生了幻读现象。


所以可重复读无法完全避免幻读，
一是当前读和快照读间无法避免幻读
二是快照读内，单用一个readview，仍然可以改变undolog使得readview读取新版本。
