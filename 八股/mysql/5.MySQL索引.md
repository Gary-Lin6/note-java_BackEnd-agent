前面我们一直讨论的是mysql的事务，它保证了处理一堆sql语句时的ACID特性。现在我们来讨论提高mysql查询效率的秘密：索引

# 一.基本概念

## 1什么是索引？为什么需要索引
索引是帮助 MySQL 高效获取数据的数据结构（有序）。在数据之外，数据库系统还维护着满足特定查找算法的数据结构，这些数据结构以某种方式引用（指向）数据，这样就可以在这些数据结构上实现高级查询算法，这种数据结构就是索引。

## 2索引的分类
### 2.1按数据结构分

>[!info] 为什么innoDB引擎默认选择B+Tree 索引

要知道为什么选B+树，而不选其他的什么二叉搜索树，平衡二叉搜索树，红黑树，B树。
我们首先得了解他们是什么。
这里重点介绍B树和B+树
**什么是B树**
B树其实就是M（M>=2）叉搜索树，它的每个节点都挂着一个数据。

**什么是B+树**
B+树就是B树升级版。
它的所有数据都挂在叶子节点上，非叶子节点只有索引。（解决b树前面搜索时会读无用数据的缺点）
并且，它的叶子节点间维护着一个有序的双向链表。（解决了b树遍历只能中序遍历的缺点）

**为什么选B+树**
1.相比于二叉树，B+树分支更少，层级更少，每次查询I/O次数更少，效率更高
2.相比于B树，B树的非叶子节点和叶子节点都要存数据，B+树非叶子节点存索引，叶子节点才存数据，相同次I/O查询，B+树查得数据更多，效率更快。而且，B+树叶子节点维护了双向链表，适用于MySQL范围查询，而B+树要想范围查询只能中序遍历。
3.相比于Hash索引（哈希表），哈希索引只能等值查询，不能范围查询。
综上选用B+树

### 2.2按物理存储分

| 分类                    | 含义                            | 特点         |
| --------------------- | ----------------------------- | ---------- |
| 聚集索引(Clustered Index) | 将数据存储与索引放一块，索引结构的叶子节点保存了行数据   | 必须有，而且只有一个 |
| 二级索引(Secondary Index) | 将数据与索引分开存储，索引结构的叶子节点关联的是对应的主键 | 可以存在多个     |
**每一张表都有且只有一个聚集索引，那么MySql会选哪一列作为聚集索引呢？**
- 如果有主键，默认会使用主键作为聚簇索引的索引键（key）；
- 如果没有主键，就选择第一个不包含 NULL 值的唯一列作为聚簇索引的索引键（key）；
- 在上面两个都没有的情况下，InnoDB 将自动生成一个隐式自增 id 列作为聚簇索引的索引键（key）；

**选什么作为二级索引：**
自己创建的索引。

>[!info] 什么是回表查询？

要理解什么是回表查询，先要清楚查询过程是怎样的？
根据聚集索引进行查询：对聚集索引的B+树查询，然后返回叶子上所挂着的数据。
根据二级索引进行查询：对二级索引的B+树查询，得到主键后（二级索引叶节点挂着的是主键），再回到聚集索引的B+树，根据得到的主键进行查询，最后得到主键对应叶子节点上的数据。

那么这个获取完主键，再回主键索引B+树查询的过程，叫做回表。

**对二级索引查询一定会回表吗？**
不一定，如果二级索引叶子节点已经有要的数据就不用再回表查询了。比如说要查询的就是主键，比如说二级索引是个联合索引，查的值就是索引中的一部分（后面会提到索引失效，这也有可能要回表）

### 2.3按字段特征分类
| 分类   | 含义                         | 特点           | 关键字      |
| ---- | -------------------------- | ------------ | -------- |
| 主键索引 | 针对于表中主键创建的索引               | 默认自动创建，只能有一个 | PRIMARY  |
| 唯一索引 | 避免同一个表中某数据列中的值重复           | 可以有多个        | UNIQUE   |
| 常规索引 | 快速定位特定数据                   | 可以有多个        |          |
| 全文索引 | 全文索引查找的是文本中的关键词，而不是比较索引中的值 | 可以有多个        | FULLTEXT |
### 2.4按字段个数分类
从字段个数的角度来看，索引分为单列索引、联合索引（复合索引）。

- 建立在单列上的索引称为单列索引，比如主键索引；
- 建立在多列上的索引称为联合索引；

**怎么建立/查看/删除索引**
```MySQL
#如果不加 CREATE 后面索引类型参数，则创建的是常规索引
#主键索引会自动创建
CREATE [ UNIQUE | FULLTEXT ] INDEX index_name ON table_name (index_col_name, ...);

#查看索引
SHOW INDEX FROM table_name;

#删除索引
DROP INDEX index_name ON table_name;
```

# 二.索引使用规则
## 1.最左前缀法则：
如果索引关联了多列（联合索引），要遵守最左前缀法则，最左前缀法则指的是查询从索引的最左列开始，并且不跳过索引中的列。

>[!info] 为什么要遵循最左前缀法则

因为联合索引B+树排序规则是这样的：按照最左边的列（指创建联合索引时，写在括号最左边的那个，可以是原表后面的列）排序。如果相同，再按下一列排序，依次类推。
因此，如果跳过了某一列，那么后面的排序可能就不是有序的了，不能按照索引来查询。

**example**
比如，如果创建了一个 (a, b, c) 联合索引，如果查询条件是以下这几种，就可以匹配上联合索引：

where a=1；
where a=1 and b=2 and c=3；
where a=1 and b=2；
需要注意的是，因为有查询优化器，所以 a 字段在 where 子句的顺序并不重要。
也就是where b=2 and a=1也可以利用索引

但是，如果查询条件是以下这几种，因为不符合最左匹配原则，所以就无法匹配上联合索引，联合索引就会失效:

where b=2；
where c=3；
where b=2 and c=3；

## 2.满足最左前缀法则仍失效情况
### 2.1联合索引范围查询
联合索引有一些特殊情况，并不是查询过程使用了联合索引查询，就代表联合索引中的所有字段都用到了联合索引进行索引查询，也就是可能存在部分字段用到联合索引的 B+Tree，部分字段没有用到联合索引的 B+Tree 的情况。

**example1**
select * from t_table where a > 1 and b = 2，联合索引（a, b）哪一个字段用到了联合索引的 B+Tree？

ans：a用到索引，b没用到。
理解：什么时候能用到索引，什么时候不能用。
能n（n>=2）分查询就说明能用索引

例如这道题，查询的过程是这样的：先根据a>1,定位到第一个满足条件的叶子节点，然后再向后扫描，看每个节点的b等不等于2直到某个字段不满足a>1(but因为a是从小到大排，后面都满足而已)。
因此a用了索引（对a查询其实是做了几次n分查询），b没有。

**example2**
select * from t_table where a = 1 and b > 2，联合索引（a, b）哪一个字段用到了联合索引的 B+Tree？

ans:a和b都用到了索引
查询过程：先根据a=1查询到第一个满足条件的a，然后从后扫描，直到遇到不满足a=1条件的节点。然后，扫描到的节点用二分查询，查到第一个b>2的节点，后面节点即为所求。
因此ab都用了索引

**example3**
select * from t_table where a >= 1 and b = 2，联合索引（a, b）哪一个字段用到了联合索引的 B+Tree？

ans:ab都用了
因为a>=1其实分成了a=1和a>1,a>1部分b没有用到索引，但a=1部分b用到了索引。

**example4**
SELECT * FROM t_table WHERE a BETWEEN 2 AND 8 AND b = 2，联合索引（a, b）哪一个字段用到了联合索引的 B+Tree？

ans：ab都用了
between and相当于a>=2 and a<=8,同example 3

### 2.2联合索引模糊匹配
模糊查询中，如果仅仅是尾部模糊匹配，索引不会失效；如果是头部模糊匹配，索引失效。

理解：因为字符串类型模糊匹配是根据字典序排序的（即从左往右，按a-z排序）如果头部都是模糊匹配了，根本就不能用b+树进行搜索。但尾部排序还能根据头部进行搜索。

### 2.3运算操作
在索引列上进行运算操作，索引将失效。
如：explain select * from tb_user where substring(phone, 10, 2) = '15';​
理解：这查的是函数操作后满足条件的索引，你无法用n分法划分哪部分满足条件哪部分不满足条件，因此只能进行全表扫描，看看每个索引是否满足条件

字符串类型字段使用时，不加引号，索引将失效。(相当于发生隐性转换，进行了运算操作)
如：explain select * from tb_user where phone = 17799990015;，此处phone的值没有加引号

### 2.4or
用 or 分割开的条件，如果 or 其中一个条件的列没有索引，那么涉及的索引都不会被用到

### 2.5MySQL 评估
如果 MySQL 评估使用索引比全表更慢，则不使用索引

## 3.不满足最左前缀法则仍可能触发复合索引的情况
只是可能触发，优化器可能仍选择全表扫描。

#### 3.1 覆盖索引

当查询的字段完全包含在联合索引中，即使 `WHERE` 条件不满足最左前缀，MySQL 可能选择 全索引扫描（而非全表扫描）来直接返回数据例如：

索引（a,b,c），`SELECT b, c FROM table WHERE b = 10;`，数据可直接从索引中提取（无需回表），优化器可能选择扫描整个索引。

#### 3.2 索引下推（ICP）

MySQL 5.6+ 支持 ICP，当查询条件包含部分联合索引列时，即使不满足最左前缀，存储引擎层仍会利用索引过滤数据，减少回表次数，例如：

索引（a,b,c），`SELECT * FROM table WHERE a = 1 AND c = 3;`，a 作为最左前缀生效，c 的条件通过 ICP 在存储引擎层过滤。

- 索引下推（ICP）需在 MySQL 5.6+ 且开启 `optimizer_switch=index_condition_pushdown=on`
    
#### 3.3 排序/索引优化

若 ORDER BY 或 GROUP BY 的字段顺序与联合索引一致，即使 WHERE 条件不满足最左前缀，仍可能利用索引优化排序或分组，例如：

索引（a,b），`SELECT * FROM table WHERE a > 1 ORDER BY b;`，索引 (a, b) 天然按 a, b 排序，优化器可能选择索引避免 filesort。

#### 5.6.4 范围查询后的等值查询

若查询条件中 最左前缀为范围查询，后续列的等值条件可能仍会使用索引，例如：

索引（a,b,c），`SELECT * FROM table WHERE a > 1 AND b = 2;`，索引会先按 a 的范围查找，再匹配 b 的等值条件（需结合索引下推）。
