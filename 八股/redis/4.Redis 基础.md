# 一.Redis 线程模型

## 1.Redis单线程？命令处理
### 1.1Redis哪些部分用单线程？为什么
执行命令部分使用单线程。redis 6.0前网络I/O单线程

**为什么？**
redis在内存进行操作，执行速度已经很快了，再加上redis有高效的数据模型，所有redis性能瓶颈不在于cpu。并且，如果引入多线程，那么线程上下文切换会有额外开销，额外开销消耗的时间会导致多线程效率还不如单线程。再加上如果有多线程，那么要考虑线程并发问题，就要加锁等操作，更影响性能。综上，redis执行命令部分使用单线程

### 1.2Redis网络模型
Redis 6.0 版本之前，是用的是单Reactor单线程的模式
![[Pasted image 20260516205755.png]]
到 Redis 6.0 之后，就将网络 IO 的处理改成了多线程的方式，这是因为随着网络硬件的性能提升，Redis 的性能瓶颈有时会出现在网络 I/O 的处理上。

所以为了提高网络 I/O 的并行度，Redis 6.0 对于网络 I/O 采用多线程来处理。

## 2.Redis多线程？关闭文件、AOF 刷盘、释放内存

### 2.1哪些部分用了多线程，为什么？
关闭文件、AOF 刷盘，释放内存这三个任务，redis会单独创建线程来完成

**为什么**
因为这些任务比较耗时，如果都放在主线程来做，容易造成阻塞

**怎么做**
后台线程相当于一个消费者，生产者把耗时任务丢到任务队列中，消费者（BIO）不停轮询这个队列，拿出任务就去执行对应的方法即可。

## 3.I/O多路复用
### 3.1什么是I/O多路复用
下面介绍5种I/O模型
>[!info] 阻塞I/O

![[Pasted image 20260516210427.png]]
请求数据，如果请求不到，一直阻塞，直到数据返回

>[!info] 非阻塞I/O

![[Pasted image 20260516210531.png]]
一直轮询数据是否准备好，直到数据返回。
你就说是不是没阻塞吧。。

>[!info] I/O多路复用

对于阻塞I/O，非阻塞I/O，他们一次只能查询一个数据，后面要查询的数据一直被拖着。导致效率很低。I/O多路复用就是为了解决这个问题的。
I/O多路复用通过一个线程监听多个文件（操作系统一切皆是文件，socket也是文件），当某个文件可读时，通知该线程，就可以直接获取该文件的数据了
![[Pasted image 20260516211037.png]]

>[!info] 信号驱动I/O

与IO复用（select、poll、epoll）相比，信号驱动IO通过信号机制实现IO操作的异步通知，不需要进程主动调用轮询函数来检查IO状态
![[Pasted image 20260516211354.png]]

>[!info] 异步I/O

异步IO的整个过程都是非阻塞的，用户进程调用完异步API后就可以去做其它事情，内核等待数据就绪并拷贝到用户空间后才会递交信号，通知用户进程：
![[Pasted image 20260516211427.png]]

### 3.2为什么Redis要用I/O多路复用
因为 Redis 是跑在「单线程」中的，所有的操作都是按照顺序线性执行的，但是由于读写操作等待用户输入 或 输出都是阻塞的，所以 I/O 操作在一般情况下往往不能直接返回，这会导致某一文件的 I/O 阻塞导，致整个进程无法对其它客户提供服务。而 I/O 多路复用就是为了解决这个问题而出现的。为了让单线程(进程)的服务端应用同时==处理多个客户端==的事件，Redis 采用了 IO 多路复用机制。

### 3.3到底在哪用了I/O多路复用
答案是网络连接
这里“多路”指的是多个网络连接客户端，“复用”指的是复用同一个线程(单进程)。I/O 多路复用其实是使用一个线程来检查多个 Socket 的就绪状态，在单个线程中通过记录跟踪每一个 socket（I/O流）的状态来管理处理多个 I/O 流。如下图是 Redis 的 I/O 多路复用模型：
![[Pasted image 20260516211757.png]]
整个文件事件处理器是在单线程上运行的，但是通过 I/O 多路复用模块的引入，实现了同时对多个 FD 读写的监控，当其中一个 client 端达到写或读的状态，文件事件处理器就马上执行，从而就不会出现 I/O 堵塞的问题，提高了网络通信的性能。

# 二.Redis缓存淘汰和过期删除
redis可以给键值对设置过期时间，当过期时间到时，会触发过期删除机制，惰性删除+定期删除过期key
当内存满时，redis会触发缓存淘汰策略，淘汰一些不必要内存资源

## 1.缓存淘汰策略
maxmemory：redis可用内存，超过了触发redis内存淘汰策略，默认为3G
缓存淘汰策略共8种
![[Pasted image 20260516212812.png]]
- 不进行数据淘汰：内存满时，不删除数据，而是直接报错
- 进行数据淘汰：
	- 在设置过期时间的数据内淘汰：
		- **volatile-random**：随机淘汰设置过期时间的数据
		- **volatile-ttl**：优先淘汰快过期的数据
		- **volatile-lru**：优先淘汰最久没用的数据
		- **volatile-lfu**：优先淘汰最少使用的数据
	- 在所有数据内淘汰：
		- **allkeys-random**：随机淘汰
		- **allkeys-lru**：淘汰最久没用数据
		- **allkeys-lfu**：淘汰整个键值中最少使用的键值。

### 1.1淘汰过程
具体见下图

![[Pasted image 20260516214435.png]]

过程解释：内存不足时，先判断淘汰策略进不进行数据淘汰，不进行直接报错，进行则判断是从所有数据还是从有过期时间数据中淘汰。选择不同数据集。
然后判断是随机策略还是LRU,LFU,TTL策略。随机策略则随机选key删除。
其他策略则准备一个evicion_pool,一个db一个db遍历（redis总共有16个db），随机挑选maxmemory_samples个数据。按不同策略，往idleTime存不同值，判idleTime符不符合要求放入evicition_pool中。最后倒叙删除eviction_pool里的数据。
然后判断内存满不满足要求，不满足则重复。

>[!info] LRU,LFU怎么实现？

Redis的数据都会被封装为一个redisObject，其中的unsigned lru:LRU_BITS属性用来统计当前RedisObject对象的访问信息，根据配置文件中配置的淘汰策略会记录不同的值：​
•若采用LRU淘汰策略，该字段会以秒为单位记录最近一次访问时间，长度24bit​
•若采用LFU淘汰策略，该字段会用高16位 以分钟为单位记录最近一次访问时间，低8位记录逻辑访问次数

![[Pasted image 20260516220502.png]]
Redis会通过unsigned lru:LRU_BITS统计一个key最近一次的访问时间或最近一次访问的频率，其中LFU策略的逻辑访问次数并不是key的真实访问次数，而是通过计算得到：​
•生成0~1之间的随机数R​
•计算 1 / (旧次数 * lfu_log_factor + 1)，记录为P，lfu_log_factor默认为10​
•如果 R < P ，则计数器 + 1，且最大不超过255​
•访问次数会随时间衰减，距离上一次访问时间每隔 lfu_decay_time 分钟（默认为1），计数器 -1​

随着该key的访问次数增多，得到的P越来越小，R<P的可能就越来越小，该key的逻辑访问次数增加的可能也会越来越小。如果长时间不访问，访问次数会随时间衰减。逻辑访问次数虽然不是真正访问次数，但是对所有key来说，这个次数还是能说明一个key的访问频率的高低。

## 2.过期删除机制
Redis 选择「惰性删除+定期删除」这两种策略配和使用，以求在合理使用 CPU 时间和避免内存浪费之间取得平衡。

==惰性删除==：在访问一个key的时候，检查该key的存活时间，如果已经过期才执行删除
![[Pasted image 20260516221502.png|215]]
但是如果很多key过期后很长时间没有被访问，只采用惰性删除时，这些key就无法被释放，这就需要周期删除。

==周期删除==：**每隔一段时间「随机」从数据库中取出一定数量的 key 进行检查，并删除其中的过期key。**
间隔时间：10s
抽多少：20个
删除过程：随机抽20个key，逐个判断过没过期，如果过期，删除，最后统计删除个数，如果本轮检查的已过期 key 的数量，超过 5 个（20/4），也就是「已过期 key 的数量」占比「随机抽取 key 的数量」大于 25%，则继续重复步骤 1；如果已过期的 key 比例小于 25%，则停止继续删除过期 key，然后等待下一轮再检查。
为了保证删除循环过度,设置循环最长时间：25ms，超时则删除循环结束。

# 三.大Key问题
## 1.什么是大key以及其引发的问题
**什么是大key**
通常认为字符串类型的key对应的value值占用空间大于1M，或者集合类型的k元素数量超过1万个，就算是大key。

**大key问题**
- 内存占用过高，导致内存不足，触发内存淘汰策略
- 性能下降：对于大key的读写等操作占用更多cpu时间和内存资源，导致redis性能下降。又因为redis执行命令是单线程操作，甚至会阻塞其他操作
- 网路阻塞：每次获取大key产生的网络流量较大，可能造成机器或局域网的带宽被打满，同时波及其他服务。这也会造成主从同步延迟，因为主从连接后是长连接，传递大key消耗时间长，会导致主从同步的延迟

## 2.如何检测和处理bigkey
**如何检测**
1. --bigkeys 参数检测
2. scan 命令
3. 开源工具检测rdb文件
4. 公有云检测

**如何处理**
- 对大Key进行拆分。例如将含有数万成员的一个HASH Key拆分为多个HASH Key，并确保每个Key的成员数量在合理范围。在Redis集群架构中，拆分大Key能对数据分片间的内存平衡起到显著作用。
- 手动异步删除：对大Key进行清理。将不适用Redis能力的数据存至其它存储，并在Redis中删除此类数据。注意开启lazyfree:将该操作交给单独的子线程处理，避免阻塞主线程。
- 采用合适的数据结构：例如，文件二进制数据不使用 String 保存、使用 HyperLogLog 统计页面 UV、Bitmap 保存状态信息（0/1）。
- 对过期数据进行定期清。堆积大量过期数据会造成大Key的产生，例如在HASH数据类型中以增量的形式不断写入大量数据而忽略了数据的时效性。可以通过定时任务的方式对失效数据进行清理。
