# 一.数据结构
## 1.SDS（动态字符串）
### 1.为什么要有SDS
C语言也有字符串，为什么还要专门设计一个数据类型来存储字符串呢？
因为：
1. 获取字符串长度的时间复杂度为 O（N）；
2. 字符串的结尾是以 “\0” 字符标识，字符串里面不能包含有 “\0” 字符，因此不能保存二进制数据；
3. 字符串操作函数不高效且不安全，比如有缓冲区溢出的风险，有可能会造成程序运行终止；
因此，SDS就是来解决以上痛点的

### 2.SDS的具体实现
![[Pasted image 20260505191635.png|271]]
结构中的每个成员变量分别介绍下：

- <span style="color:blue;">len，记录了字符串长度</span>。
	这样获取字符串长度的时候，只需要返回这个成员变量值就行，时间复杂度只需要 O（1）。
- <span style="color:blue;">alloc，分配给字符数组的空间长度</span>。
	 这样在修改字符串的时候，可以通过 `alloc - len` 计算出剩余的空间大小，可以用来判断空间是否满足修改需求，
	 如果不满足的话，就会自动将 SDS 的空间扩展至执行修改所需的大小，然后才执行实际的修改操作，所以使用 SDS 既不需要手动修改 SDS 的空间大小，也不会出现前面所说的缓冲区溢出的问题。
- <span style="color:blue;">flags，用来表示不同类型的 SDS</span>。
	 一共设计了 5 种类型，分别是 sdshdr5、sdshdr8、sdshdr16、sdshdr32 和 sdshdr64，后面在说明区别之处。
- <span style="color:blue;">buf[]，字节数组，用来保存实际数据</span>。
	 不仅可以保存字符串，也可以保存二进制数据。

总的来说，Redis 的 SDS 结构在原本字符数组之上，增加了三个元数据：len、alloc、flags，用来解决 C 语言字符串的缺陷。

>[!info] sds不发生缓冲区溢出的原因及动态扩容机制

通过 `alloc - len` 计算，可以算出剩余可用的空间大小，这样在对字符串做修改操作的时候，就可以由程序内部判断缓冲区大小是否足够用。

而且，当判断出缓冲区大小不够用时，Redis 会自动将扩大 SDS 的空间大小，以满足修改所需的大小。
扩容机制：
- 如果所需的 sds 长度小于 1 MB，那么最后的扩容是按照翻倍扩容来执行的，即 2 倍的newlen
- 如果所需的 sds 长度超过 1 MB，那么最后的扩容长度应该是 newlen + 1MB。
这样的好处是，下次在操作 SDS 时，如果 SDS 空间够的话，API 就会直接使用「未使用空间」，而无须执行内存分配，有效的**减少内存分配次数**。

>[!info] 节省内存空间

SDS 结构中有个 flags 成员变量，表示的是 SDS 类型。

Redis 一共设计了 5 种类型，分别是 sdshdr5、sdshdr8、sdshdr16、sdshdr32 和 sdshdr64。

这 5 种类型的主要区别就在于，它们数据结构中的 len 和 alloc 成员变量的数据类型不同。
![[Pasted image 20260505192555.png]]
存不同长短的字符串时，sds类型不同，len和alloc的数据类型也不同，从而节省了空间

## 2.intset（整数集合）
### 1.为什么要有intset
因为c里面没有实现set集合
而redis要实现set数据类型，设计了intset，以保证整数集合元素唯一，有序
### 2.intset具体实现
**结构体定义：**
```c
typedef struct intset {
    //编码方式
    uint32_t encoding;
    //集合包含的元素数量
    uint32_t length;
    //保存元素的数组
    int8_t contents[];
} intset;
```
可以看到，保存元素的容器是一个 contents 数组，虽然 contents 被声明为 int8_t 类型的数组，但是实际上 contents 数组并不保存任何 int8_t 类型的元素，contents 数组的真正类型取决于 intset 结构体里的 encoding 属性的值。

如果 encoding 属性值为 INTSET_ENC_INT16，那么 contents 就是一个 int16_t 类型的数组，数组中每一个元素的类型都是 int16_t；
如果 encoding 属性值为 INTSET_ENC_INT32，那么 contents 就是一个 int32_t 类型的数组，数组中每一个元素的类型都是 int32_t；
如果 encoding 属性值为 INTSET_ENC_INT64，那么 contents 就是一个 int64_t 类型的数组，数组中每一个元素的类型都是 int64_t；
![[Pasted image 20260505193551.png]]

>[!info] 整数集合升级操作：

如果新加入的元素，大小超过了编码方式的范围，则要进行升级

- 升级编码为能容纳新元素的新编码，并按照新的编码方式及元素个数扩容数组
- 倒序依次将数组中的元素拷贝到扩容后的正确位置（正着扩容则要多次挪动元素，慢）
- 将待添加的元素放入数组末尾
- 最后，将inset的encoding属性改为新的编码方式，将length属性改为length+1

升级操作的好处：节省内存
**不支持降级操作**

>[!info] 集合元素唯一，有序

使用二分查找是否重复及插入位置

## 3.Dict（字典）
### 1.Dict具体实现
Dict由三部分组成，分别是：哈希表（DictHashTable）、哈希节点（DictEntry）、字典（Dict）
#### 1.1dictht,dictEntry
**dictht哈希表**
```c
typedef struct dictht {
    //哈希表数组
    dictEntry **table;
    //哈希表大小
    unsigned long size;  
    //哈希表大小掩码(size-1)，用于计算索引值
    unsigned long sizemask;
    //该哈希表已有的节点数量
    unsigned long used;
} dictht;
```

可以看到，哈希表是一个数组（dictEntry ** table），数组的每个元素是一个指向「哈希表节点（dictEntry）」的指针。
![[Pasted image 20260505195848.png]]
>[!info] 为什么要sizemask

计算插入位置方便，hash&sizemask即为插入位置。
其实与java，hashmap设计思路相同，详见[[java基础#为什么哈希表的长度为$2 n$]]

**dictEntry哈希节点**

```c
typedef struct dictEntry {
    //键值对中的键
    void *key;
  
    //键值对中的值
    //用union存储值，可能是指针，可能是有/无符号整数，可能是小数，不用多个定义，节省内存
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;
    //指向下一个哈希表节点，形成链表
    struct dictEntry *next;
} dictEntry;
```

>[!info] 解决哈希冲突：链式哈希

实现的方式就是每个哈希表节点都有一个 next 指针，用于指向下一个哈希表节点，因此多个哈希表节点可以用 next 指针构成一个单项链表，被分配到同一个哈希桶上的多个节点可以用这个单项链表连接起来，这样就解决了哈希冲突。

但是，如果数据量大的话，在一个桶上的哈希节点连成链表，查询复杂度退化成O(n),这时候就需要扩容
而扩容的秘密在于dict的实现
#### 1.2dict
![[Pasted image 20260505201553.png]]
![[Pasted image 20260505201626.png]]

>[!info] rehash

Dict中的HashTable就是数组结合单向链表的实现，当集合中元素较多时，必然导致哈希冲突增多，链表过长，则查询效率会大大降低。
rehash除了扩容之外，还可以收缩
**扩容时机**
Dict在每次新增键值对时都会检查负载因子（LoadFactor = used/size） ，以下两种情况都会触发哈希表扩容：
- 哈希表的 LoadFactor >= 1，并且服务器没有执行 BGSAVE 或者 BGREWRITEAOF 等后台进程
- 哈希表的 LoadFactor > 5
**收缩时机**
Dict除了扩容以外，每次删除元素时，也会对负载因子做检查，当LoadFactor < 0.1时，会做哈希表收缩

**rehash过程**
在正常服务请求阶段，插入的数据，都会写入到「哈希表 1」，此时的「哈希表 2 」 并没有被分配空间。
相应正常情况下的删除元素也是删哈希表1的元素

随着插入数据越来越多，或删除数据到一定程度
1. 计算新hash表的realeSize，值取决于当前要做的是扩容还是收缩：
    -  如果是扩容，则新size为第一个大于等于dict.ht[0].used + 1的2^n
    -  如果是收缩，则新size为第一个小于等于dict.ht[0].used的2^n （不得小于4）
2. 按照新的realeSize申请内存空间，创建dictht，并赋值给dict.ht[1]
3. 设置dict.rehashidx = 0，标示开始rehash
4. 将dict.ht[0]中的每一个dictEntry都rehash到dict.ht[1]
5. 将dict.ht[1]赋值给dict.ht[0]，给dict.ht[1]初始化为空哈希表，释放原来的dict.ht[0]的内存
6. 将rehashidx赋值为-1，代表rehash结束

![[Pasted image 20260505202800.png]]
但是rehash是在执行增删操作时判断是否要执行rehash，而这些操作是在Redis的主进程中进行的，若一次迁移太多的entry会导致主进程阻塞，直至完成rehash后才能处理新命令。

因此，Dict的rehash并不是一次性完成的，如果entry太多，rehash就可能导致主进程阻塞，因此实际Dict的rehash是分多次、渐进式的完成，因此称为**渐进式rehash**。

>[!info] 渐进式rehash

1.计算新的realeSize，（2^n)
2.按照新的realeSize申请内存空间，创建dictht，并赋值给dict.ht[1]​
3.设置dict.rehashidx = 0，标示开始rehash​

==4.==每次执行增删改查时，都检查一下 dict.rehashidx 是否大于-1，如果是则将dict.ht[0].table[rehashidx]的entryl链表rehash到dict.ht[1]，并且将rehashidx++，直至dict.ht[0]的所有数据都rehash到dict.ht[1]
​
5.将dict.ht[1]赋值给dict.ht[0]，给dict.ht[1]初始化为空哈希表，释放原来的dict.ht[0]的内存​
6.将rehashidx赋值为-1，代表rehash结束​

==7.==在rehash过程中，新增操作，则直接写入ht[1]，查询、修改和删除由于不确定数据在dict.ht[0]还是dict.ht[1]，会在dict.ht[0]和dict.ht[1]依次查找并执行命令，这样可以确保ht[0]的数据只减不增，随着rehash最终为空

rehashidx作用：
- 标志正在rehash
- 标志渐进rehash到哪了

## 4.ziplist（压缩链表）
### 1.为什么要有ziplist
正常实现双向链表，要用两个指针指向前一个和后一个数据，内存占用大，使用ziplist，可以节省空间
### 2.ziplist具体实现
#### 2.1ziplist结构
ziplist虽然叫链表，但实际是用数组来实现的
![[Pasted image 20260505204355.png]]

- zlbytes：类型uint32_t，长度4 字节，
	- 记录整个压缩列表占用的内存字节数​
- zltail：类型uint32_t，长度4 字节，
	- 记录压缩列表表尾节点距离压缩列表的起始地址有多少字节，
	- 通过这个偏移量，可以确定表尾节点的地址​
- zllen：类型uint16_t，长度2 字节，
	- 记录了压缩列表包含的节点数量。
	- 最大值为UINT16-MAX（65534），如果超过这个值，此处会记录为65535，但节点的真实数量需要遍历整个压缩列表才能计算得出​
- entry：压缩列表包含的各个节点，节点的长度由节点保存的内容决定，长度不定​
- zlend：类型uint8_t，长度1 字节，特殊值0xFF（十进制255），用于标记这是压缩列表的末端

#### 2.2ziplistEntry结构
ZipList 中的Entry并不像普通链表那样记录前后节点的指针，因为记录两个指针要占用16个字节，浪费内存。而是采用了下面的结构：
![[Pasted image 20260505204726.png]]
- previous_entry_length：前一个节点的长度，占1个或5个字节
    - 如果前一节点的长度小于254字节，则采用1个字节来保存这个长度值
    - 如果前一节点的长度大于254字节，则采用5个字节来保存这个长度值，第一个字节为0xfe，后四个字节才是真实长度数据
        
- encoding：编码属性，记录content的数据类型（字符串还是整数）以及长度，占用1个、2个或5个字节
- contents：负责保存节点的数据，可以是字符串或整数

要获得下一节点的地址，只需用 当前节点的地址 + entry 的长度即可；​
要获得前一结点的地址，只需用 当前节点的地址 - previous_entry_length 即可；

>[!info] encoding编码属性

**字符串**
![[Pasted image 20260505205039.png]]
根据字符串的长度大小，encoding 会使用 1 字节/2字节/5字节的空间进行编码，encoding 编码的前两个 bit 表示数据的类型，后续的其他 bit 标识字符串数据的实际长度，即 data 的长度。
**整数**
![[Pasted image 20260505205140.png]]
如果encoding是以“11”开始，则证明content是整数，且encoding固定只占用1个字节

### 3.ziplist的缺陷

#### 3.1存储过多的元素时，查找中间元素效率低下
在压缩列表中，如果我们要查找定位第一个元素和最后一个元素，可以通过表头三个字段（zllen）的长度直接定位，复杂度是 O(1)。
而查找其他元素时，就没有这么高效了，只能逐个查找，此时的复杂度就是 O(N) 了，因此压缩列表不适合保存过多的元素。

#### 3.2连锁更新
ZipList的每个Entry都包含previous_entry_length字段来记录上一个节点的大小。这个字段的长度是1个或5个字节
现在假设一个压缩列表中有多个连续的、长度在 250～253 之间的节点，如下图：
![[Pasted image 20260505205743.png]]
因为这些节点长度值小于 254 字节，所以 prevlen 属性需要用 1 字节的空间来保存这个长度值。

这时，如果将一个长度大于等于 254 字节的新节点加入到压缩列表的表头节点，即新节点将成为 e1 的前置节点，如下图：
![[Pasted image 20260505205834.png]]
因为 e1 节点的 prevlen 属性只有 1 个字节大小，无法保存新节点的长度，此时就需要对压缩列表的空间重分配操作，并将 e1 节点的 prevlen 属性从原来的 1 字节大小扩展为 5 字节大小。
导致e1大小超过254字节，导致e2prevlen改变，e2大小超过254字节，导致e3prevlen改变...

ZipList这种特殊情况下产生的连续多次空间扩展操作称之为连锁更新。
空间扩展操作也就是重新分配内存，因此连锁更新一旦发生，就会导致压缩列表占用的内存空间要多次重新分配，这就会直接影响到压缩列表的访问性能。

但如果节点数量少，就算发生了连锁更新，对性能影响也不到

因此，结合2.1和2.2，ziplist只适合存储节点数量不多的情况

## 5.QuickList（快表）
### 1.为什么要有QuickList
前面提到ZipList节点数量过多时会产生性能问题，所以需要限制ZipList的长度和entry大小，
若要存储大量数据，超出ZipList最佳上限，就需要使用多个ZipList分片存储数据，这时就要一个数据结构用来管理这些ZipList分片，
QuickList就是用来管理多个ZipList，保证他们之间联系的数据结构。

### 2.QuickList具体实现
quicklist的实现是：双向链表+ziplist
![[Pasted image 20260505211732.png]]
#### 2.1quicklist结构:
```c
typedef struct quicklist {
    //quicklist的链表头
    quicklistNode *head;      //quicklist的链表头
    //quicklist的链表尾
    quicklistNode *tail; 
    //所有压缩列表中的总元素个数
    unsigned long count;
    //quicklistNodes的个数
    unsigned long len;       
    //ziplistEntry上限
    int fill:QL_FILL_BITS;
    //首尾不压缩的节点数量
    unsigned int compress:QL_BM_BITS;
    //bookmark:用于内存重分配的书签，一般不用
} quicklist;
```
>[!info] fill不同值含义

•正值代表ZipList的允许的entry个数的最大值​
•负值代表ZipList的最大内存大小，分5种情况：​
	-1：每个ZipList的内存占用不能超过4kb​
	-2：每个ZipList的内存占用不能超过8kb​
	-3：每个ZipList的内存占用不能超过16kb​
	-4：每个ZipList的内存占用不能超过32kb​
	-5：每个ZipList的内存占用不能超过64kb

>[!info] compress不同值含义

- 0：特殊值，代表不压缩
- 1：标示QuickList的首尾各有1个节点不压缩，中间节点压缩
- 2：标示QuickList的首尾各有2个节点不压缩，中间节点压缩
- ......以此类推

#### 2.2quickListNode结构
```c
typedef struct quicklistNode {
    //前一个quicklistNode
    struct quicklistNode *prev;     //前一个quicklistNode
    //下一个quicklistNode
    struct quicklistNode *next;     //后一个quicklistNode
    //quicklistNode指向的压缩列表
    unsigned char *zl;              
    //压缩列表的的字节大小
    unsigned int sz;                
    //压缩列表的元素个数
    unsigned int count : 16;        //ziplist中的元素个数 
    //一些与压缩有关参数
    ....
} quicklistNode;
```

![[Pasted image 20260505212842.png]]

quicklist通过fill参数控制每个ziplist的大小，避免单个ziplist过大。
且用双向链表来链起多个压缩链表，
	如果插入操作导致quicklistNode中的元素数量超过了一定的阈值，则将该节点拆分成两个新节点
	如果删除操作导致quicklistNode中的元素数量过少，Redis会将相邻的两个节点合并成一个节点。
最后，还能通过压缩，进一步节省内存

## 6.skipList（跳表）
### 1.为什么需要skipList
跳表结合了集合高效查询和链表快速增删的优点，
既保持了数据的有序性，又提供了快速的访问速度。

### 2.skipList的具体实现
因为链表查询，一次只能跳一个节点，所以查询效率为O（1），那如果一次不止跳一步呢？
我们设计多层级，有的跳1步，有的跳多步，就能实现快速查询的功能了
![[Pasted image 20260505213937.png]]
![[Pasted image 20260505214110.png]]

#### 2.1zskiplist结构
即ziplistNode的头节点
```c
typedef struct zskiplist {
	//头尾节点
    struct zskiplistNode *header, *tail;
    //长度
    unsigned long length;
    //最大层级数
    int level;
} zskiplist;
```

#### 2.2zskiplistNode结构
头节点也是zskiplistNode，只不过没有权重和节点值
```c
typedef struct zskiplistNode {
    //节点值
    sds ele;
    //元素权重值
    double score;
    //后向指针
    struct zskiplistNode *backward;
  
    //节点的level数组，保存每层上的前向指针和跨度
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;
    } level[];
} zskiplistNode;
```

### 3.ziplist查询，插入，删除过程
>[!info] 查询过程

1.从最高层开始，通过前进指针逐层查找​
2.如果当前节点下一个节点不存在，则向下移动
3.
- 如果当前节点的下一个节点的权重小于要查找的权重，则向右移动；
- 如果大于要查找的权重，则向下移动​，
- 如果等于要查找的权重，判断是不是目标值，是则返回，不是则判断sds大小，大于向下移动，小于向右移动
5.重复上述过程，直到找到目标节点或确定目标节点不存在

>[!info] 插入过程

- 首先进行查找操作，找到插入位置
- 随机生成该节点的层数，每一层都插入该新节点
- 更新相关节点的前进指针和跨度

**为什么要随机生成层数**
如果某一层节点数过少，就会向下一层查询，导致查询效率降低，因此相邻层数间节点个数比为1：2时比较适合。
但如果固定比例的话，维持比例带来的花销比较大。使用随机数生成层数，只要调好生成层数概率，即可做到近似1：2的效果。

**怎么随机**
具体的做法是，跳表在创建节点时候，会生成范围为[0-1]的一个随机数，如果这个随机数小于 0.25（相当于概率 25%），那么层数就增加 1 层，然后继续生成下一个随机数，直到随机数的结果大于 0.25 结束，最终确定该节点的层数。

这样的做法，相当于每增加一层的概率不超过 25%，层数越高，概率越低，层高最大限制是 64。

### 4.为什么用跳表不用平衡树
- <span style="color:blue;">从内存占用上来比较，跳表比平衡树更灵活一些。</span>
	- 平衡树每个节点包含 2 个指针（分别指向左右子树），而跳表每个节点包含的指针数目平均为 1/(1-p)，具体取决于参数 p 的大小。如果像 Redis里的实现一样，取 p=1/4，那么平均每个节点包含 1.33 个指针，比平衡树更有优势。
- <span style="color:blue;">在做范围查找的时候，跳表比平衡树操作要简单。</span>
	- 在平衡树上，我们找到指定范围的小值之后，还需要以中序遍历的顺序继续寻找其它不超过大值的节点。如果不对平衡树进行一定的改造，这里的中序遍历并不容易实现。而在跳表上进行范围查找就非常简单，只需要在找到小值之后，对第 1 层链表进行若干步的遍历就可以实现。
- <span style="color:blue;">从算法实现难度上来比较，跳表比平衡树要简单得多。</span>
	- 平衡树的插入和删除操作可能引发子树的调整，逻辑复杂，而跳表的插入和删除只需要修改相邻节点的指针，操作简单又快速。


## 7.RedisObject
### 1.为什么需要RedisObject
Redis中的所有数据都是以key-value的形式存放的，存放一个key-value结构需要存储三个内容，key、value、key和value的映射关系，key使用一个存储结构SDS动态字符串就足够了，映射关系通过dict字典维护，但是value包含5种基本的类型（string、list、hash、set、sortedset），为了在同⼀个dict内能够存储不同类型的value，需要一个通用的数据类型，这就是**redisObject**，简写为robj，Redis中所有value都被存储为redisObject类型。

RedisObject的作用：
- 统一对象管理：为Redis中的各种数据类型提供统一的接口，使得Redis能够以一致的方式处理不同类型的数据
- 内存优化：通过引用计数和LRU机制，实现了自动内存管理和淘汰策略，有效地节省了内存空间，提高了内存利用率
- 操作一致性：为不同类型的数据提供了统一的操作接口，如获取对象类型、编码方式、值等，保证了操作的一致性
### 2.RedisObject具体实现
```c
typedef struct redisObject {​
    unsigned type:4; // 数据类型，如字符串、列表、哈希等​
    unsigned encoding:4; // 编码方式，如int、raw、hashtable等​
    unsigned lru:LRU_BITS; // Least Recently Used，用于记录对象最近被访问的时间​
    int refcount; // 引用计数，用于自动内存管理​
    void *ptr; // 指向实际存储数据的指针​
} robj;
```
- type：表示数据对象的类型，用4bit位表示，对应着Redis的五基本数据类型，string、hash、list、set和zset
```C
#define OBJ_STRING 0
#define OBJ_LIST 1
#define OBJ_SET 2
#define OBJ_ZSET 3
#define OBJ_HASH 4
```

- encoding：底层编码方式，共有11种，占4个bit位，不同的编码方式对应不同的存储结构

Redis中会根据存储的数据类型不同，选择不同的编码方式，共包含11种不同类型：

| **编号** | **编码方式**                | **说明**        |
| ------ | ----------------------- | ------------- |
| 0      | OBJ_ENCODING_RAW        | raw编码动态字符串    |
| 1      | OBJ_ENCODING_INT        | long类型的整数的字符串 |
| 2      | OBJ_ENCODING_HT         | hash表（字典dict） |
| 3      | OBJ_ENCODING_ZIPMAP     | 已废弃           |
| 4      | OBJ_ENCODING_LINKEDLIST | 双端链表          |
| 5      | OBJ_ENCODING_ZIPLIST    | 压缩列表          |
| 6      | OBJ_ENCODING_INTSET     | 整数集合          |
| 7      | OBJ_ENCODING_SKIPLIST   | 跳表            |
| 8      | OBJ_ENCODING_EMBSTR     | embstr的动态字符串  |
| 9      | OBJ_ENCODING_QUICKLIST  | 快速列表          |
| 10     | OBJ_ENCODING_STREAM     | Stream流       |
Redis有五种基本的数据类型，每种数据类型的使用的编码方式如下：

| **数据类型**   | **编码方式**                                   |
| ---------- | ------------------------------------------ |
| OBJ_STRING | int、embstr、raw                             |
| OBJ_LIST   | LinkedList和ZipList(3.2以前)、QuickList（3.2以后） |
| OBJ_SET    | intset、HT                                  |
| OBJ_ZSET   | ZipList、HT、SkipList                        |
| OBJ_HASH   | ZipList、HT                                 |
- lru：记录对象最近被访问的时间，占用24个bit位，用于实现LRU策略（最近最少使用策略）的内存淘汰
- refcount：对象引用计数器，通常占用4个字节，用于自动内存管理。当引用计数为0时，表示对象可以被释放。Redis通过引用计数来管理内存，避免内存泄漏
- ptr：指向实际存储数据的指针，根据不同的数据类型和编码方式，指向不同的数据结构，32位系统占用4字节，64位系统占用8字节

## 1.String
### 1.具体实现
String是Redis中最常见的数据存储类型：

- 基本编码方式是**RAW**，基于简单动态字符串（SDS）实现，存储上限为512mb
![[Pasted image 20260506193823.png]]

- 如果存储的SDS长度小于44字节，则会采用**EMBSTR**编码，此时RedisObject对象头和SDS是一段连续空间，申请内存时只需要调用一次内存分配函数，效率更高
![[Pasted image 20260506193833.png]]

>[!info] 为什么是44字节？

SDS头信息中len、alloc、flags各占一字节，字符结束符`\0`占一字节，字符串内容44字节，整个SDS共占48字节，RedisObject头信息共占16字节，加起来是64字节，
Redis中jemalloc是默认的内存分配器，Jemalloc会为不同大小的内存请求分配固定大小的块（这些块的大小通常是2的幂次），在分配内存时会尽量满足内存对齐的要求，以减少由于频繁的内存分配和释放操作导致的内存碎片。
64字节刚好是Jemalloc的一个内存分配单位，能把这些数据存储在一个连续的内存块中而不产生内存碎片。

- 当存储的字符串是整数值，并且大小在LONG_MAX范围内，则会采用**INT**编码，直接将数据保存在RedisObject的ptr指针位置，不再需要SDS：

![[Pasted image 20260506194001.png]]

- 如果整数值超过了LONG_MAX的范围，就会使用**ROW**编码方式，把整数当成字符串存储

## 2.List
List类型与Java中的LinkedList类似，可看作一个双向链表结构，支持正向检索和反向检索，特点如下：
- 有序（指按插入先后顺序）
- 元素可以重复
- 插入和删除快
- 查询速度一般
### 1.具体实现
Redis的List类型需要从首、尾操作列表中的元素，而且支持根据索引查询，哪个数据结构满足这些要求？

- LinkedList ：普通链表，可以从双端访问，内存占用较高，内存碎片较多
- ZipList ：压缩列表，可以从双端访问，内存占用低，存储上限低
- QuickList：LinkedList + ZipList，可以从双端访问，内存占用较低，包含多个ZipList，存储上限高
    
在3.2版本之前：Redis采用**ZipList和LinkedList**来实现List，当元素数量小于512并且元素大小小于64字节时采用**ZipList**编码，超过则采用LinkedList编码。

## 3.Set
Set 类型是一个无序并唯一的键值集合，它的存储顺序不会按照插入的先后顺序进行存储。

一个集合最多可以存储 2^32-1 个元素。概念和数学中个的集合基本类似，可以交集，并集，差集等等，所以 Set 类型除了支持集合内的增删改查，同时还支持多个集合取交集、并集、差集。
![[Pasted image 20260506200235.png]]
Set 类型和 List 类型的区别如下：

List 可以存储重复元素，Set 只能存储非重复元素；
List 是按照元素的先后顺序存储元素的，而 Set 则是无序方式存储元素的
### 1.具体实现
Set 类型的底层数据结构是由**哈希表**或**整数集合**实现的：

- 如果集合中的元素都是整数且元素个数小于 512 （默认值，set-maxintset-entries配置）个，Redis 会使用整数集合作为 Set 类型的底层数据结构；
- 如果集合中的元素不满足上面条件，则 Redis 使用哈希表作为 Set 类型的底层数据结构。

**为什么？**
要保证集合内的元素唯一，上述数据结构里只有intset和哈希表满足。
**哈希表存的不是键值对吗？怎么用来存单个数呢？**
key存值，value为null即可。

## 4.Zset
Zset 类型（有序集合类型）相比于 Set 类型多了一个排序属性 score（分值），对于有序集合 ZSet 来说，每个存储元素相当于有两个值组成的，一个是有序集合的元素值，一个是排序值。

有序集合保留了集合不能有重复成员的特性（分值可以重复），但不同的是，有序集合中的元素可以排序。
### 1.具体实现
ZSet也就是SortedSet，其中每一个元素都需要指定一个score值和member值：

- 可以根据score值排序
- member必须唯一
- 可以根据member查询分数
    
因此，zset底层数据结构必须满足键值存储、键必须唯一、可排序，哪种编码结构可以满足？

- SkipList：可排序，并且可以同时存储score和ele值（member），但无法保证键的唯一性，也无法快速根据member找score（只能遍历）
- HT（Dict）：可以键值存储，并且可以根据key找value，但无法排序


Zset底层同时使用了这两种编码结构，结合它们的功能满足Zset的需要，ZSet的结构定义如下，在创建ZsetObject对象时，先创建了Zset对象，再为Zset对象创建了Dict和SkipList，并将编码方式设置为**OBJ_ENCODING_SKIPLIST**：
![[Pasted image 20260506201439.png]]
![[Pasted image 20260506201446.png]]

>[!info] 为什么既有哈希表又有跳表？

因为zset支持根据元素查分数的操作，跳表查询效率为O（logn），而哈希表效率为O(1)，所以要有哈希表

>[!info] 还要有ZipList?

当元素数量不多时，HT和SkipList的优势不明显，而且更耗内存，同一份数据存储了两份。因此zset还会采用ZipList结构来节省内存，不过需要同时满足两个条件：
1. 元素数量小于`zset_max_ziplist_entries`，默认值128
2. 每个元素都小于`zset_max_ziplist_value`字节，默认值64

但是ziplist本身没有排序功能，而且没有键值对的概念，因此需要通过逻辑编码实现：​
•ZipList是连续内存，因此score和element是紧挨在一起的两个entry，element在前，score在后​
•score越小越接近队首，score越大越接近队尾，按照score值升序排列

# 三.总结
redis是以key-value形式存储数据，对于key，我们用sds方式存储，对于key与value间映射关系，我们用dict存储，对于value，因为有多种数据类型，我们用redisobject类型同一存储，用type表示数据类型，用encoding表示编码方式，用ptr指向存储地址。
所以数据类型其实是指value的数据类型。

对于String类型，因为要存储字符串，数字等，又因为 C语言字符串的缺陷，所以设计出SDS数据结构来存储。但是实际上，字符串不一定都用SDS来存储
- 对于整数数据，如果在long范围内，直接将数据存在ptr位置。
- 如果字符串长度过小，会采用embstr编码方式，不用ptr，而是将字符串拼接在redisObject头后面
- 其他则用ptr指向存储对应字符串的SDS数据结构

对于List类型，因为要实现链表结构，很自然想到用LinkedList,最基础的链表实现。但要是存储数据过多，就会想到用ziplist来实现。
但因为ziplist的缺陷，redis后面统一用quicklist来实现

对于set类型，要实现集合元素唯一的效果，很自然想起intset，但是因为intset只能存整数，所以又会想到dict也就是哈希表来存储，只用key，不用value，就能够实现元素唯一的效果。

对于zset类型，要实现元素唯一，且可排序，并且元素还带分数。很自然就想到用跳表。但是因为要实现查分数的效果，又会想到用哈希表。只不过，在元素较少时，跳表和哈希表的效率和压缩链表差不多，但压缩链表的占用比这两少得多，于是，在元素较小较少时，用压缩链表实现，只需维持压缩链表连续两个元素，前一个为element，后一个是score即可，并且保证压缩链表有序性即可。

对于hash类型。相当于zset不用排序版，所以不需要跳表，只用哈希表就能够实现，并且，和zset理由相同，元素较小较少时，用压缩链表实现即可。
