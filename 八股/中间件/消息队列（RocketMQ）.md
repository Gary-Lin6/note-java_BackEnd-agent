
# 一.消息队列基础
## 1.什么是消息队列，为什么要用消息队列
消息队列可以理解成存储信息的一个队列，生产者将消息丢进消息队列中，可以转头做自己的业务。然后消息队列再将里面的信息推给消费者，让消费者去完成相应的业务。
![[Pasted image 20260609184836.png]]
它有三大好处：
1. 应用解耦：以订单消费系统为例，
	- 在没有消息队列的时候，一个订单的完成要经历资格校验，扣库存，生成订单几步。这些代码高度耦合在一起，要是中间某一步失败了，那么整个订单就生成失败。抑或是某天，我想在扣库存和生成订单中间，加一步发短信通知，那就要改动原先代码，相当麻烦。
	- 而在有消息队列后，只要资格校验通过，它就往消息队列丢一条消息，而扣库存，生成订单这些业务逻辑作为消费者，监听消息队列，一旦收到消息，就开始自己的工作。要是某时刻负责生成订单的机子宕机了，对于订单完成是没有影响的，只要后续将生成订单的机子重新起起来，再插入订单即可。抑或是要添加一个新业务，只用新建一个消费者，去监听消息队列即可。
2. 异步提速：相信看了上面的例子，我们会发现，资格校验和生成订单这些步骤异步完成了。原先，可能生成订单要对数据库插入数据，很慢。有了消息队列之后，只要完成资格校验，就算你下单完成，直接给用户返回结果，用户体验大大提升。
3. 削峰填谷：当高并发场景下，如果没有消息队列，一下子几万的请求会打入数据库，数据库压力会很大。而有了消息队列之后，这些对数据库的操作就会存到消息队列中，逐步让消费者取出操作数据库。将并发的操作分散开来，减轻了数据库的压力，达到削峰填谷的效果。

>[!info] 既然操作队列那么好，为什么不每个项目都用？

1. 可用性降低：消息队列是中间件。如果消息队列发生宕机，那么整个业务链路将瘫痪，所以为了保证整个系统的高可用，你将不得不保证消息队列的高可用。
2. 业务处理更复杂：后面我们会提到，消息队列可能有消息重复问题，这就使得业务处理要保证幂等性（重复操作不改变结果）
3. 数据一致性：可能生产者发消息给消息队列，认为事务完成了，但消费者处理消息时失败了。造成了数据不一致的问题

## 2.基本概念：
### 2.1NameServer与Broker
在RocketMQ中有两个重要的角色
- NameServer：就相当于一个注册中心
- Broker：RocketMQ服务端
当RocketMQ服务端，也就是Broker在启动的时候，会往NameServer注册自己的信息
![[Pasted image 20260609192423.png]]
这些信息其中就包括
- 当前Broker所在机器的ip和端口
- 当前Broker管理的Topic的名称以及每个Topic有几个队列

当生产者和消费者启动的时候，就会从NameServer拉取这些信息，这样生产者和消费者就可以通过NameServer中获取到Broker的ip和端口，跟Broker通信了
### 2.2Topic与Queue
- Topic:可以理解为一类消息的集合。
- queue：“存储”消息的队列。
一个topic默认有四个队列。当该topic集合内的消息发过来时，会根据一定的算法，分配到某个queue中。
而queue是在broker里的，也就是说，生产者发送莫个topic时，会根据从NameServer获取到该Topic对应的Broker，发给那个broker，然后broker再根据算法，分给对应的broker里某个queue。
而消费者，根据从nameserver里获取的某个topic的broker的ip地址，订阅相对应的broker，从而获取信息。

**实际写代码中，topic不是生产者自己订的吗？nameserver怎么知道生产者订的topic会发到哪个broker？**
其实对于第一次遇到的topic，nameserver也会根据算法去分配某个broker，然后后续都用这个broker即可。

### 2.3消费者与消费者组
消费者组中有多个消费者，不同消费者组之间消费消息是互不干扰的。
在同一个消费者组中，消息消费有两种模式。
- 集群模式
- 广播模式
**集群模式**
同一条消息只能被同一个消费组下的一个消费者消费，也就是说，同一条消息在同一个消费者组底下只会被消费一次，这就叫集群消费。

集群消费的实现就是将队列按照一定的算法分配给消费者，默认是按照平均分配的。
![[Pasted image 20260609194915.png]]
每个消费者对应自己相应的queue，因为消息是分到某个queue中的，所以只有相应queue的消费者能获取到该消息，因此体现为一个消息只能被一个消费者组下的一个消费者消费。
rocketmq默认为集群模式

**广播模式**
广播模式就是同一条消息可以被同一个消费者组下的所有消费者消费。

其实实现也很简单，就是将所有队列分配给每个消费者，这样每个消费者都能读取topic底下所有的队列的数据，就实现了广播模式。
![[Pasted image 20260609195108.png]]
从这里我们可以看出，消费者处理消息是以消息队列为单位的。生产者发送消息是以broker为单位的。

>[!info] 消费者是怎么获取消息的？

rocketmq采用长轮询的方法或许消息
**消费者发送拉去请求到Broker，如果此时有消息，则Broker直接响应返回消息，如果没消息就hold住这个请求，比如等15s，在15s内如果有消息就立马响应返回消息，如果没消息就返回无消息。**

## 3.消息类型
1. 同步消息：及时性比较强，重要的消息，且必须要有回执（发送后阻塞等待Broker确认）
2. 异步消息：及时性没那么强，但需要有回执（发送后不阻塞，继续执行后续业务，使用sendCallBack异步接收结果）
3. 单向消息：不需要有回执的消息（发送消息后无返回结果）
4. 延时消息：发送后延迟一段时间到达消息队列
5. 批量消息：一次发送批量的消息
6. 顺序消息：生产者发送消息的顺序跟消费者消费消息的顺序是一致的（后续会讲）
7. 事务消息：生产者发消息给broker后，broker不马上传给消费者，而是等生产者完成事务后，根据事务的提交或是回滚再决定是传给消费者还是丢掉（后面会讲）


## 4.消息存在哪？
当消息被Broker接收到的时候，Broker会将消息存到本地的磁盘文件中，保证Broker重启之后消息也不丢失

RocketMQ给这个存消息的文件起了一个高大上的名字：CommitLog
由于消息数据可能会很大，同时兼顾内存映射的效率，不可能将所有消息都写到同一个文件中，所以CommitLog在物理磁盘文件上被分为多个磁盘文件，每个文件默认的固定大小是1G。

![[Pasted image 20260609200450.png]]
当生产者将消息发送过来的时候，就会将消息按照顺序写到文件中，当文件空间不足时，就会重新建一个新的文件，消息写到新的文件中。

![[Pasted image 20260609200509.png]]
消息在写入到文件时，除了包含消息本身的内容数据，也还会包含其它信息，比如

- 消息的Topic
- 消息所在队列的id，前面提到过
- 消息生产者的ip和端口
...
这些数据会和消息本身按照一定的顺序同时写到CommitLog文件中
![[Pasted image 20260609200549.png]]

>[!info] 什么时候写入commitlog？

对于这个问题，rocketmq有两种方案：
- 同步刷盘
- 异步刷盘
**同步刷盘**
当生产者发消息给broker时，会直接将消息写入commitLog中，然后再回生产者ACK。

**异步刷盘**
当生产者发消息给broker后，broker会直接回生产者ACK，同时有一个后台线程根据设置：比如默认事件，去进行刷盘。

同步刷盘相对于异步刷盘来说消息的可靠性更高，因为异步刷盘可能出现消息并没有成功刷到磁盘时，机器就宕机的情况，此时消息就丢了；但是同步刷盘需要等待消息刷到磁盘，那么相比异步刷盘吞吐量会降低。所以同步刷盘适合那种对数据可靠性要求高的场景。


## 5.Consumer Queue
在RocketMQ中，消息的消费单元是以队列来的
所以RocketMQ为了方便快速的查找和消费消息，会为每个Topic的每个队列也单独创建一个文件
RocketMQ给这个文件也起了一个高大上的名字：ConsumeQueue

当消息被存到CommitLog之后，其实还会往这条消息所在队列的ConsumeQueue文件中插一条数据
每个队列的ConsumeQueue也是由多个文件组成，每个文件默认是存30万条数据

插入ConsumeQueue中的每条数据由20个字节组成，包含3部分信息

- 消息在CommitLog的起始位置（8个字节）
- 消息在CommitLog存储的长度（8个字节）
- 消息tag的hashCode（4个字节）
![[Pasted image 20260609203424.png]]
每条数据也有自己的编号（offset），默认从0开始，依次递增

当消费者拉取消息的时候，会告诉服务端自己消费哪个队列（queueId），哪个位置的消息（offset）的消息

服务端接收到消息之后，会找到queueId对应的ConsumeQueue，然后找到offset位置的数据，最后根据这条数据到CommitLog文件查找真正的消息内容。

## 6.RocketMQ的重传机制
Rocket MQ信息处理流程正常来说是这样的：
![[Pasted image 20260609212128.png]]
生产者产生消息后，MQ返回ACK确认。生产者继续完成接下来的业务。
随后MQ向消费者发送消费消息，消费者收到消息后回回复一个ACK确认。

**什么时候重传**
当生产者发消息后，如果MQ没有回ACK，那么生产者会认为MQ没有收到消息，那么就会进行消息的重传（运输层应该用的TCP）。
MQ向消费者发消息后，如果消费者没有回ACK，那么MQ会进行重传。

**重传频率和重传次数**
- 顺序消息的消费重试
对于顺序消息，为了保证消息消费的顺序性，当consumer消费失败后，消息队列会自动不断进行消息重试(每次间隔时间为 1s)，

这时会导致consumer消费被阻塞的情况，故必须保证应用能够及时监控并处理消费失败的情况，避免阻塞现象的发生

- 无序消息的消费重试
对于无序消息（普通、定时、延时、事务消息），当消费者消费消息失败时，您可以通过设置返回状态达到消息重试的结果。

无序消息的重试只针对集群消费方式生效；广播方式不提供失败重试特性，即消费失败后，失败消息不再重试，继续消费新的消息。
设置里最多重传16次，且一次比一次事件长。重传完16次后，该信息会被移到死信队列。

**死信队列**
当一条消息初次消费失败，消息队列 RocketMQ 会自动进行消息重试；达到最大重试次数后，若消费依然失败，则表明消费者在正常情况下无法正确地消费该消息，此时，消息队列 RocketMQ 不会立刻将消息丢弃，而是将其发送到该消费者对应的特殊队列中。

在消息队列 RocketMQ 中，这种正常情况下无法被消费的消息称为死信消息（Dead-Letter Message），存储死信消息的特殊队列称为死信队列（Dead-Letter Queue）。

死信队列：
- 不会再被消费者正常消费。
- 有效期与正常消息相同，均为 3 天，3 天后会被自动删除。因此，请在死信消息产生后的 3 天内及时处理。
# 二.Rocket MQ常见问题
## 1.Rocket MQ怎么保证消息的顺序性
要保证消息的顺序性，我们要思考，为什么消息会无序？
因为对于同一个topic的消息，即使按顺序发出，也会根据一定算法分到不同的queue。而我们又知道，消费者是对一个queue消费的。那么有的消费者消费速度快，可能先完成了那个queue的消息，有的消费速度慢，别的queue都消费完了，它还没完成。导致在后面的消息提前被消费，造成顺序的不一致。
```
生产者发5个消息：
queue1 :5 1
queue2: 2
queue3:3
queue4:4
消费者对queue1消费快：
1 5 2 3 4(消息错乱)
```
这里我们会发现造成消息无序最主要原因是，
1. 生产者没有把消息发到同一个queue中。
2. 但除此以外，如果broker不能保证队列里的顺序，那消费者读取出来也是无序的。
3. 最后，如果那个queue被多个消费者消费，那同样也会因为消费者快慢而造成消息无序。

- 所以要解决消息顺序性的问题，生产者要发顺序消息：即实现一个**MessageQueueSelector**，以将按顺序的几个消息发到同一个queue里（比如用对消息公共id取模）
- 而broker单线程写入commitLog的方式，也天然保证了queue内的有序性
- 消费者方面我们要实现有序消费模式，同时如果消费者里有多个线程时，对消息的处理要加锁，以保证有序性。

## 2.RocketMQ怎么保证数据一致性（怎么处理分布式事务，事务消息是什么？）
Rocket MQ信息处理流程正常来说是这样的：
![[Pasted image 20260609211442.png]]
生产者产生消息后，MQ返回ACK确认。生产者继续完成接下来的业务。
随后MQ向消费者发送消费消息，消费者收到消息后回回复一个ACK确认。

在RocketMQ重传机制的基础上，我们来思考，怎么保证数据的一致性。
也就是怎么保证生产者和消费者的业务同成功或同失败。

我们考虑消费者失败的情况，如果消费者失败了，那么将不会回ACK响应。那么消息队列就会重传消息给消费者，直到消费者回复ACK，或者重传次数达到最大16次。对于后者，我们会人工处理死信队列的信息，所以我们一般假设，只要消息成功发给mq，消费者一般能成功。

所以只用考虑生产者情况，正常情况下，生产者丢了个消息并收到ACK后，就去完成剩下的业务了。那如果接下来的业务出错呢？对于正常的信息，生产者无法挽回，就会造成生产者出错，消费者正确的数据不一致的情况。

为此，我们有事务消息：
![[Pasted image 20260609212909.png]]
**事务消息流程**
1. 生产者先发一个HALF_MESSAGE给MQ，MQ收到后回一个ACK给生产者
2. 但MQ并不急着将消息给消费者而是等待事务回一个结果给MQ。
3. 生产者收到ACK确认后继续执行本地业务，在执行业务的过程中，根据结果，回COMMIT或ROLL_BACK,UNKNOW(一般不会)给broker。
	- 如果是commit：mq就将消息给消费者
	- 如果是rollback:就把消息丢掉。
	- 如果是unknow：说明是什么网络错误，根据业务需求决定是丢掉，还是给人工处理
4. 如果生产者执行事务时间很长，那么mq就会主动去询问生产者，这时，又会会commit，rollback或者unknow：
	- 如果是commit：mq就将消息给消费者
	- 如果是rollback:就把消息丢掉。
	- 如果是unknow：说明是什么网络错误，根据业务需求决定是丢掉，还是给人工处理

## 3.RocketMQ怎么保证信息不被重复消费（使用消息队列怎么保证幂等性）
首先为什么消息会被重复消费，还是因为重传机制。
- 生产者重传：
	- 如果MQ已经收到了消息了，但回复的ACK丢包了，导致生产者重传了，会使信息重复。
	- 如果MQ回ACK时，生产者宕机了，重启后发现信息没传重新传来一遍，会导致信息重复。
- MQ重传
	- 如果消费者收到消息，但回的ACK丢包了，导致MQ重传了，会使消息被重复消费
	- 如果消费者回ACK时，MQ宕机了，重传时发现信息没传会重传，导致信息被重复消费。
对于生产者重传问题，RocketMQ会根据消息生成唯一消息id，避免消息的重复。
但是，对于MQ重传问题，虽然说MQ宕机可以用rocketMQ集群保证，但ACK丢包的情况你是无法解决的。所以要解决消息不被重复消费问题，要从消费者这边入手。

我们要保证业务的消息幂等性。

>[!info] 消息幂等性

当业务多次消费到同一条消息的结果与消费一次的结果是相同的，同时多次消费同一条消息并未对业务系统产生任何负面影响，那么这个消费者的处理过程就是幂等的。

>[!info] 常见实现消息幂等性的方法


![[Pasted image 20260610130305.png]]
对于天然幂等的方法，可以不用额外处理，对于不幂等的方法，要保证其消息幂等。

假设我们业务的消息消费逻辑是：插入某张订单表的数据，然后更新库存
```
insert into t_order values .....
update t_inv set count = count-1 where good_id = 'good123';
```
最容易想到的方法是在插入和更新前，先判断是否插入，如果插入了说明消息重复了，直接不做。
```
select * from t_order where order_no = 'order123'   
if(order  != null) {
	return ;//消息重复，直接返回
}
```
但对于高并发的场景（两条消息同时抵达消费者），如果两个线程同时select * from t_order where order_no = 'order123'   ,都查到没有，就会都新增。

很容易想到的解决方案是加锁。这里既可以加悲观锁，也可以加乐观锁。
- 悲观锁：可以在java层锁住查询语句。也可以在select语句后面加上 for update，给mysql加上行锁。这样多个查询就会互斥，从而达到只有一个线程能插入并更新。
- 乐观锁：如果是对于更新语句而言，可以在表上加一个版本号，根据版本号实现乐观锁。

这些方法都要基于业务，不同业务实现方法不同，那有没有通用的方法呢？

### 3.1基于mysql（关系型数据库）通用方法1
我们可以利用数据库事务的特性，在数据库里新建一个表，叫做消息表。
具体过程是这样的：
1. 开启事务
2. 向消息表中插入该消息，相同消息的主键要相同。（最好以业务id为主键，因为可能消息队列中有手动重发的消息，messageid不同）
	- 如果插入成功，则处理相关业务
	- 如果插入失败，则说明消息处理完成，直接返回。
3. 结束事务。

**可能会有疑问，如果处理中的消息发生错误了怎么办？**
因为包裹在事务中，所以如果发生错误会回滚，使消息表中的消息撤回。后续重发的消息就会继续这个操作，直至完成业务。

**为什么放在事务里就不怕冲突了？**
因为mysql如果是可重复以上的隔离机制。向mysql中插入数据时，会加行锁。别的数据再插入时，会被阻塞。后续等某个事务完成后，如果事务成功了，新插入的数据会因为主键冲突而插入失败。如果事务失败了，会因为回滚，使得原先插入的消息被撤回，此时插入成功的消息继续完成事务。

**但是这里有它的局限性**
1. 消息的消费必须是仅依赖于关系型数据库，如果消费的消费过程中还涉及其他数据的修改，例如Redis这种不支持事务特性的数据源，则这些数据是不可回滚的。
2. 数据库必须是在一个库，跨库无法解决
3. 事务降低了并发，效率低

### 3.2基于关系型数据库改进方法
我们可以不依赖于事务，而是在消息表上加一个字段：已消费，消费中。
并且我们注意到只要插入的数据主键会发生冲突，那么插入就是幂等的。
所以实现流程如下：
![[Pasted image 20260610134448.png|427]]
执行步骤：
1. 向消息表中插入消息（state== “消费中”），同样的相同消息的主键相同
	- 插入成功，则处理业务代码。
	- 插入失败，则取出消息表中的消息，看消息状态是消费中还是已消费。
		- 如果是已消费，则直接返回mq消费成功
		- 如果是消费中，返回mq延迟消费。
2. 处理业务时
	- 如果处理成功，则更新消息表状态为成功。
	- 如果失败，则删除消息表记录，并返回mq延迟消费。

**为什么要设置过期时间**
因为处理业务时，可能发生宕机，如果发生宕机，那么将无法删除消息表记录，造成消息丢失。

**为什么没插入的数据检测到消费中，要发延迟消费给mq？这样不更是消息重复了吗**
延迟消费的意思是让mq过段时间再发这条消息给消费者。因为可能消息处理时发生了宕机，没有消息重发的话就会造成消息丢失。

## 4.RocketMQ信息积压怎么办
这里分两种情况，
- 对于实时性要求不高的消息：
	- 优先优化消费者，看看是不是有什么慢sql等拖慢了性能
	- 然后在让消费者慢慢处理即可。
- 对于实时性要求较高的消息，要优先救急：
	- 先去看一个消费者对应几个message queue，如果是一个消费者对应多个queue的话，可以采用新增消费者的方式，来处理积压的消息。
	- 但如果已经是极限了，已经一个消费者对应一个queue了，那么可以新建一个topic，这个topic里面多建一些queue。然后写一个非常简单的“搬砖程序”：该程序非常简单，就是把旧topic的消息发到新topic里去。因为该程序很简单，消费速度快，所以消息很快会被转发到新topic里去。又因为新topic队列多，所以可以创建更多的消费者去处理掉这些消息。等处理完成后，可以根据性能追求，选择将发送者转发到新topic还是转发到旧topic去。
	- 最好要检查，究竟是因为topic队列建少了，还是消费者需要优化。进行进一步的改进。
