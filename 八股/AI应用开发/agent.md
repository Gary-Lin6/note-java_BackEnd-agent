# 一.agent基本概念
## 1.什么是agent，与LLM有什么区别
agent=LLM+tool+memory+plan

传统的LLM，只能问答，并不能自主帮你做事。
而agent，本质其实是个循环，用户传入一个任务，agent中的LLM分析这个任务，计划调用哪个工具执行，返回工具调用，工具调用完后，返回结果给llm，llm将结果追加到上下文。接着继续分析是否完成任务，没完成继续循环，完成则退出并返回结果。

## 2.agent与workflow区别，联系与选择

**什么是workflow**
workflow是程序员自己编写的流程，什么情况走什么分支是固定的。
**什么是agent**
agent相当于让LLM做决定走什么流程，让ai自己决定下一步干什么。

**区别**
workflow更死板，如果遇到未设想的情况会导致工作流崩溃。但workflow更稳定，出现问题更容易排查。
而agent更灵活，遇到复杂模糊问题能更好的应对。但缺点是如果出错难以排查是哪一步出现了问题。

**联系**
其实agent内部就是一个workflow：llm-should_continue-tool，三者不断循环，让llm自己判断是否完成任务，退出循环。
而workflow的节点也可以是agent，当遇到复杂问题时，将问题拆分成多个步骤，有的步骤固定死可以让简单节点来做。复杂步骤将节点替换成agent，让agent来解决这些问题。

**选择**
如果问题解决步骤固定，能用简单workflow就用workflow。
如果问题复杂多变，可以用agentic workflow：简单来说就是将workflow中的重要节点转换成agent。

## 3.agent设计范式
agent设计范式可以理解成agent内部的workflow，llm到底怎么工作？走一步看一步？先做好每一步的计划再一步步完成？还是做完一个任务后反思后继续？以上三种流程即为agent设计范式：reAct，Plan-and-Execute，reflection

>[!info] reAct（Reasoning + Acting）

它的名字直接说明了它的核心机制：把推理（Reasoning）和行动（Acting）交替进行。具体来说，ReAct 的每一轮循环由三个步骤组成，形成一个完整的 Thought -> Action -> Observation 循环。

Thought 阶段，LLM 先把当前的情况分析一遍，把推理过程写出来，比如「用户想查竞品信息，我应该先用搜索工具查一下竞品 A 的最新动态」；
Action 阶段，LLM 根据思考的结论决定调用哪个工具、传什么参数；
Observation 阶段，工具返回的结果被反馈给 LLM，它读取这个结果，
然后进入下一轮 Thought，重新分析当前局面、决定接下来怎么做。

![[Pasted image 20260519203635.png]]

**缺点**
- 它是「走一步看一步」的模式，每一步都是局部最优决策，处理特别复杂的、需要全局规划的任务时，容易在中间迷失方向。
- 中间有错的话会直接影响到后续的所有思考和操作

>[!info] Plan-and-Execute

完美解决ReAct第一个缺点
它把规划和执行彻底分开，先让一个 LLM 专门做规划，输出一个完整的步骤列表，然后由另一个 LLM（或同一个模型以不同角色）逐步执行。

**plan固定死了吗？no！动态重规划**
![[Pasted image 20260519203500.png]]

**缺点**
如果一开始的规划就做错了，那结果大概率也是错的

>[!info] reflection

为前两种方法的质量加了层保障

它的做法是在 Agent 完成一步或者完成整个任务之后，再让一个 LLM（可以是同一个模型也可以是专门的评估模型）来判断做得好不好、结果是否符合预期。如果评估不通过，就重试或者换一种策略。

**总结反思：reflextion**
它的做法是在 Agent 完成一步或者完成整个任务之后，再让一个 LLM（可以是同一个模型也可以是专门的评估模型）来判断做得好不好、结果是否符合预期。如果评估不通过，就重试或者换一种策略。
![[Pasted image 20260519203808.png|507]]

>[!info] 三种范式怎么选？

分两个维度：任务复杂度和质量要求
任务简单，每步独立：ReAct
任务相对复杂，对质量要求相对没那么高：plan-and-execute
对质量要求高：reflection
实际运用可以混合应用。先plan-and-execute，每一步再细分成react来完成，完成后再reflction总结反思。


# 二.memory
## 1.长期记忆，短期记忆
agent记忆按时间跨度，分为**短期记忆**和**长期记忆**。
短期记忆一般指当前对话窗口对话的内容，主要实现方法是大模型自身的上下文窗口。每次对话会将上文的对话+本次对话内容合并塞给大模型，这样就实现了短期记忆的功能。
长期记忆指就算不是同一个对话窗口，大模型也能记住的内容。主要实现方法是将内容存储在向量数据库中


**上下文窗口满了怎么处理？**
- 滑动窗口：舍弃前面的对话，只保留后面几条对话内容
- 摘要压缩：上下文窗口满后，由另一个llm来总结上下文并压缩。
- 放到长期记忆里：把不常用但重要的短期记忆放到长期记忆里。

**长期记忆怎么存？**
向量数据库+embedding
Embedding 是把一段文字转化成一组数字的过程。这组数字通常有几百到几千个维度，它们共同捕捉了这段文字的「语义」。语义相近的文字，转化出来的数字向量在空间里也靠得很近。
要存长期记忆，通过embedding将原文向量化后存在向量数据库中，要取时，将提问问题也转化成向量，然后取向量数据库里接近的数据。

**长期记忆还能怎么细分？**
第一种是<span style="color:blue;">语义记忆（Semantic Memory）</span>，存的是==事实性知识==，比如「用户是 Python 开发者」「项目预算上限 5 万」，这些是不随时间变化的客观信息。

第二种是<span style="color:blue;">情节记忆（Episodic Memory）</span>，存的是==具体事件的经历==，比如「上周二用户让我写了一个爬虫，中间因为反爬策略改了三次方案」，它带有时间线和因果关系。

第三种是<span style="color:blue;">程序记忆（Procedural Memory）</span>，存的是「==怎么做某件事==」的方法论，比如「给这个用户写代码时，先确认风格偏好，再写主逻辑，最后加注释」，它更像是 Agent 积累下来的行为模式。

# 三.tool
## 1function calling
**function calling是什么**
function calling是这样一套机制：开发者定义好工具的json schema（工具规范：工具干什么，需要什么参数，返回值是什么）传给大模型，大模型判断需要调工具时，输出一段结构化的 tool_calls JSON给代码，代码拿到这个json后调用所需工具，并返回结果给大模型。大模型拿到结果再进行下一步的判断。

**为什么要function calling**
换句话说，为什么大模型要输出json语言而不是自然语言给程序来判断调用哪个工具。因为如果返回的是自然语言，由于大模型的不确定性，代码很难判断到底该调用哪个分支。而用json则一目了然，返回tool_call说明要调用工具了，name：说明调用工具（函数）的名字，参数是什么。

**LLM是怎么学会function calling的**
首先要知道ai学习的两种方法：
<span style="color:blue;">SFT（监督微调，Supervised Fine-Tuning）</span>：给模型喂大量「工具调用示范对话」，让它通过模仿学会「看到工具描述 -> 判断要不要调 -> 输出结构化 JSON 请求」这整套流程；
<span style="color:blue;">RLHF（基于人类反馈的强化学习，Reinforcement Learning from Human Feedback）</span>：收集人类对「哪种回答更好」的判断，训练一个打分器，再用这个分数反复调整模型，让它学会什么时候不应该调工具。

SFT 教会怎么调，RLHF 教会什么时候调。
![[Pasted image 20260519212502.png]]
先靠SFT大量训练，学会用json。但这样训练出来的模型不管输出什么都用json，缺乏边界感，这时用RLHF，让人来给模型不同回答打分，让模型直到什么时候该用，什么时候不该用。

RLAIF（AI Feedback）是 RLHF 的变体，用另一个 AI 代替人类标注员打分，成本更低、速度更快，现在业界也很常用，效果和人工反馈相差不大。

## 2MCP（model context protocol 模型上下文协议）
### 2.1什么是MCP，为什么要有MCP
**为什么要有MCP**
- 工具接入麻烦：不同ai应用要使用相同工具，就要复制tool到自己的代码里。
- 工具复用困难：复制的tool可能与自己本地环境不同，语言不同，维护麻烦。甚至官方不愿意放出源码，只愿意给你使用，工具复用困难。

**什么是MCP**
MCP的出现正是为了解决上述两个问题。
解决思路
- 既然是同一个tool，不同的ai应用来用，那就把tool解耦出来，放到本地或者云端。那么不同的ai，只用访问这个本地或者云端，就可以实现工具的接入。
- 那怎么解决工具复用困难问题呢？只用在本地或者云端再抽象一层，只暴露调用的接口给ai，ai使用时，调用相应的接口，就能解决工具复用困难的问题了。
那既然tool和ai应用解耦合了，那么就要规范ai应用怎么调用tool：用什么通信协议调用？用什么数据形式调用？用json的话调用工具的格式是怎么样的？等等。
MCP因此诞生：model context protocol 模型上下文协议，它本质是一个协议，用于规范ai应用怎么规范化调用本地或云端的工具。

**为什么是model context protocol？不叫function calling protocol:**
因为MCP除了能给ai调用tool之外还可以给ai一些数据库资源...提示词等，不只是调用工具。
而放在本地或云端的数据库资源，提示词，工具其实是从模型的上下文抽出来的。所以叫model context protocol

![[Pasted image 20260520205122.png]]
### 2.2MCP的底层架构
MCP 定义了三个角色，弄清楚每个角色负责什么是理解整个系统的关键。

- 先说 Host。Host 是整个系统的宿主，也就是你在用的 AI 应用本身，比如 Claude Desktop、Cursor、Windsurf。
	- Host 负责启动和管理所有 MCP Client，控制连哪些 Server、什么时候断开连接，是整个 MCP 系统的调度中心。
	- 你可以把 Host 理解成一家公司，它决定要和哪些外部供应商（Server）合作，并派出自己的联络员（Client）去对接。

- 再说 Client。Client 是 Host 内部的连接模块，一个 Client 对应一个 Server 连接。
	- 它负责三件事：初始化和 Server 的连接、向 Server 查询「你有哪些工具/资源/模板」（能力发现）、把模型的调用请求转发给 Server 并把结果带回来。
	- Client 是 Host 派出的「驻场联络员」，专门负责和某一个 Server 打交道，Host 本身不直接和 Server 说话。

- 最后是 Server。Server 是工具提供方实现的独立进程，对外暴露自己的工具、资源和提示词模板。
	- Server 完全不关心上面是哪个 Host 在用它，只需要按 MCP 协议响应 Client 的请求就行。
	- 这也是 MCP 的核心价值所在：Server 写一次，任何支持 MCP 的 Host 都能直接用，GitHub 的官方 MCP Server 不需要分别为 Claude Desktop 和 Cursor 各写一份。
![[Pasted image 20260519215201.png]]
### 2.3server除了暴露有什么tool给client，还有什么作用？
MCP Server 可以向 Client 暴露三类能力，各有各的定位。
![[Pasted image 20260519215415.png]]
先说 Tools（工具），这是最核心的能力，对应 Function Calling 里的「函数」。Tools 的本质是「有副作用的操作」，什么叫有副作用？就是执行之后会改变外部世界的状态。创建文件、提交代码、发送 Slack 消息、调用第三方 API，这些都属于 Tools，因为执行完之后环境发生了变化，而且往往不可逆。正因为如此，Tools 通常需要用户授权确认才能执行，不能让模型想调就调。

再说 Resources（资源），它和 Tools 最本质的区别就一个字：只「读」。Resources 不会改变任何东西，只是把数据提供给模型看。读取日志文件、查询数据库记录、获取文档内容，都属于 Resources 的范畴。你可以把 Resources 理解成「工具的资料室」，模型可以进去查资料，但不能修改里面的东西。正因为只读、无副作用，Resources 可以更宽松地暴露给模型，不需要像 Tools 那样谨慎授权。

最后是 Prompts（提示模板），这个能力很多人容易忽略，但在团队协作场景下特别有用。Prompts 就是预定义的提示词模板，带参数占位符，解决的是「每次都要手写重复 prompt」的问题。举个例子，你的团队有一套固定的代码审查标准 prompt，接受「编程语言」和「代码内容」两个参数，调用时只需传入参数值，就能自动展开成完整的提示词，不用每次从头写。把公司积累的优质 prompt 封装成 MCP Prompts，所有人都能复用，统一标准，这在实际工程中很实用。

### 2.4传输协议
**消息格式：JSON-RPC 2.0**
每条消息是一个 JSON 对象，
格式固定：Client 发请求时说清楚「调哪个方法、参数是什么、这次请求的 ID 是多少」，
	     Server 返回响应时带上执行结果或错误信息，通过 ID 匹配请求和响应。
用 JSON 格式的好处是易读、易调试、任何编程语言都能实现，不管 Server 是 Python 写的还是 TypeScript 写的，消息格式是一样的。

**传输方法**
- server在本地：通过stdio传输。Host 通过操作系统的管道和server通信，Server 从 stdin 读请求、把结果写到 stdout。
- server 在远程服务器上：通过**Streamable HTTP**传输（老版：「HTTP + SSE」双端点方案）
	- 「HTTP + SSE」双端点方案：一个 GET 端点开 SSE 长连接接收推送，一个 POST 端点发请求，两个端点绑在一起工作。
	- **Streamable HTTP**传输：把原来的两个端点合并成一个 /mcp 端点。Client 用 POST 发请求，Server 根据情况灵活返回：短请求直接回一个普通 JSON 响应，长请求则把这个 HTTP 响应升级为 SSE 流，持续推送中间结果。
![[Pasted image 20260519220329.png]]
### 2.5 MCP和Function calling的区别
Function calling是大模型输出结构化json调用工具的一种方法，而MCP是规范大模型调用本地，远程工具/资源等的一种协议。实现MCP协议的大模型调用工具，仍然需要function calling。
可以说function calling解决的是怎么调用的问题。而MCP解决的是规范化复用工具的问题。

## 3skill
### 3.1skill是什么？为什么需要skill
**为什么需要skill**
当你不同时期反复用ai做一件类似的事情时，你会多次输入一段差不多的prompt。
当你和伙伴合作用ai做一件类似的事情，你们会输入一份差不多的prompt，只不过有人关心这个，有人关心那个，prompt质量也不齐。
此时，你会想到，把这个prompt总结起来，放到一个文件里，每次ai运行时，就读取这个文件就可以了。
文件=skill？对吗

**什么是skill**
skill顾名思义，是ai的技巧技能，它能让==自主发现==它，==按需加载并使用==它。
实际上它是一个文件夹：内容包括
```
code-review/                  # Skill 文件夹，名字就是这个 Skill 的标识
├── SKILL.md                  # 核心指令文件（必须有）
├── scripts/                  # 可选：可执行的脚本
│   └── check_security.py     # 比如一个安全检查脚本
├── references/               # 可选：参考文档
│   └── review_standards.md   # 比如团队的审查标准文档
└── assets/                   # 可选：模板、资源文件
    └── report_template.md    # 比如审查报告的输出模板
```
其中skill.md最为关键，它分为两部分。
```markdown
//第一部分：YAML 格式的元数据，叫 frontmatter
//用以声明skill的名字，用途，触发词(可选)
--- 
name: code-reviewer 
description: Review pull request code quality. Use when the user asks to review code, check a PR, or audit code changes. Covers architecture, exception handling, security, and performance. 
triggers: 
- "review this code" 
- "帮我看看这个 PR" 
- "code review" 
---

//第二部分：正文
//用 Markdown 写具体的指令和步骤

```
而剩下三个部分可选择性加入，是ai根据skill执行时可用的资源和参考。

### 3.2skill的渐进式加载
skill与prompt除了参考和脚本外有区别外，最大的区别在于skill的渐进式加载
ai的上下文窗口不是垃圾，有的时候运行一些任务，根本不需要用到那么多的skill，将skill通通作为prompt塞入上下文根本不可行，所以skill最大的特点在于渐进式加载：
- 第一层：agent启动时，只加载skill的name和description。了解它有什么skill，以及每个skill能做什么
- 第二层：触发关键词，或ai判断某个任务需要用到某个skill了，它才将对应skill的内容加载进上下文，读取里面的步骤
- 第三层：需要时再取脚本和资源，当该skill提到对应情况需要读取资源或者运行脚本了，ai才会加载资源。

skill的渐进式加载，避免了无用skill占用大量上下文的问题。体现了skill能被agent自主发现，按需取用的特点。

### 3.3skill，MCP，function calling的区别
- function calling是ai调用工具的机制，解决ai怎么调用工具的问题
- MCP是ai调用外部工具规范化的协议，解决的是工具复用的问题
- skill是ai解决相关问题的能力，解决的是拿到工具怎么按流程解决任务的问题

# 四.Multi-agent
## 1.什么是Multi-agent,为什么需要multi-agent?
**为什么需要multi-agent**
- 单agent上下文窗口有限：任务一多，上下文窗口就满了，满了后要进行舍弃或压缩，对于后续生成质量有影响
- 单agent处理多任务能力有限：同一个 Agent 做多个任务，不如专门为各自任务配置或微调的 Agent 效果好。且一个ai做多任务，中间出错难以排查。
因此需要multi-agent。

**什么是multi-agent**
multi-agent顾名思义，就是多个agent共同完成一个任务。每个agent各有分工，按规划并行/串行执行，以处理更复杂，更长流程的任务。

## 2.Multi-agent设计方案
### 2.1中心化方案
Multi-Agent 的中心化方案，核心是一个叫 Orchestrator （交响乐指挥）的特殊角色。
工作流程：
 1. Orchestrator 接受用户指令，将大问题拆分成子问题，并将子问题分发给相应的worker agent。
 2. worker agent只关心接受到的任务，根据任务得到产出并返回给Orchestrator
 3. Orchestrator得到所有worker agent产出后，判断是否能完成任务，如果可以，则返回。如果不行则让不行的那部分worker重新完成。直到得出满意结果

**优势**
某个环节有问题可以随着Orchestrator 的调度记录，找出是哪个agent出的错误，方便排查

### 2.2去中心化方案
去中心化的思路是没有总调度，多个 Agent 通过共享的消息队列或状态空间自行协商、直接通信。

听起来很灵活，但实际上很少使用：
- 任务分配没有协调：可能A和B干了同一件事，浪费资源
- 执行顺序没有保证：如果C要等A,B完成，如果A或B产出结果单没有通知，则C将无法进行工作
- 失败没有感知：如果A出错，B,C并不能判断，只能拿着错误结果继续做
- 没有人来确认「任务整体完成了」：如果A,B,C循环依赖，那将不知道由谁来输出结果。![[Pasted image 20260521203845.png]]



## 3.Multi-agent怎么通信？A2A协议
**什么是A2A（Agent to Agent）协议**
单个 Agent 升级到 Multi-Agent 后，出现两个问题：
- Agent怎么知道别的Agent的存在及它的功能：如果用代码写死，那么新增或修改一个agent功能会相当麻烦
- Agent 之间怎么沟通：如果还靠自然语言互相聊天，Token 消耗很高，也容易出现格式解析错误。

A2A 协议就是为了解决这个问题。

>[!info] 怎么认识别的Agent：**Agent Card**

  每个 A2A Agent 都在一个约定位置发布一张 JSON 格式的名片（A2A 规范推荐的路径是 /.well-known/agent-card.json，早期版本叫 agent.json，两种路径在社区里都能看到）
  
里面写清楚自己叫什么、能做哪类任务（Skill 列表）、支不支持流式返回、支不支持异步回调（push notification，任务完成后主动通知调用方）。

  任何想和它协作的 Agent，先去拿这张名片，再决定要不要把任务委托给它。
![[Pasted image 20260521204956.png]]
这样，新增或修改一个agent，只用新增卡片或修改卡片，相当方便。

>[!info] 怎么通信？
  
当一个agent向另一个agent通信，是传达一个标准json数据，其中最重要的是task（任务协作的基本单位）
调度 Agent 把一段任务委托给另一个 Agent，就是创建一个 Task；接收方执行这个 Task；完成后把结果作为 Task 的产出（artifacts，可以是文本、文件等）返回。

**task声明周期**
![[Pasted image 20260521205435.png]]
调度agent在发布完task后，通过轮询或回调就能知道任务完成的怎么样，即发布完任务后可以去完成别的事情，实现异步长任务协作。

# 五.RAG
## 1.什么是RAG，为什么需要RAG
**什么是RAG**
**RAG（Retrieval-Augmented Generation，检索增强生成）** 顾名思义，通过检索增强生成。在向LLM提问前，先搜索事先准备好的”知识库“,将搜索到的知识与用户提的问题结合起来再问LLM，让大模型根据搜索到的知识回答，已达到增强生成的效果。

**为什么要RAG？**
- 第一是知识时效性。

预训练模型的知识会停在训练数据截止时间点。训练后发生的新事件、新政策、新产品文档，模型默认是不知道的，除非通过联网、工具调用或外部知识注入来补。RAG 的做法是动态检索外部知识源，把最新的相关内容直接送给 LLM，让它不用只依赖参数里的旧知识。

- 第二是私有数据访问。

企业内部的产品文档、知识库、客户数据，不可能让公开 LLM 随便访问。RAG 在用户提问时只提取和问题相关的片段给 LLM，不需要暴露全部数据，模型也能基于企业自己的知识回答。

- 第三是幻觉问题。

LLM 编造事实这件事大家都遇到过。RAG 通过提供明确参考文本，让模型尽量基于证据回答，确实能降低幻觉概率。但别指望它彻底消除幻觉。检索错误、上下文噪声、引用错配、模型不遵循指令，都可能导致错误答案。生产级 RAG 通常还要配引用校验、答案评估、拒答机制和人工反馈闭环。

## 2.RAG工作原理
RAG 的工程链路通常分两个阶段：离线索引和在线检索生成。索引阶段把原始文档处理成可检索的数据结构；在线阶段在用户提问时完成查询理解、检索召回、上下文构建和答案生成。
![[Pasted image 20260521211201.png]]
### 2.1离线索引
离线阶段的目标很明确：在用户提问之前，就把知识库建好。这一阶段只做一次，建好了后面反复用。
![[Pasted image 20260521211545.png]]
#### 2.1.1文档加载,清理文档，增强文档：
- 文档加载：把各种格式的原始数据读取进来，可以是 PDF、Word、Markdown、网页、数据库记录等。（用第三方api读取）
- 清理文档：去掉 HTML 标签、特殊字符等噪声。
- 增强文档：补充元数据，比如时间戳、分类标签，为后续检索提供过滤维度。
#### 2.1.2文档拆分（Chunking）：

>[!info] 文档能整篇存吗？

先说一个最重要的前提：原始文档不能直接存进向量库，必须先切成小块（chunk）再存。

第一，向量模型有输入长度限制，一般最多几百到几千 token，一篇几千字的文档根本塞不进去。

第二，就算模型支持超长输入，把整篇文章压缩成一个向量，细节信息会被「平均掉」，当你搜索某个细节，最终检索到的就是这篇笼统的文档，而不是精确的那段话，召回质量差。

>[!info] chunk是什么？结构怎么样

chunk是对原始文档的一个小划分。它包括三个部分
![[Pasted image 20260521215120.png]]
向量区记录原文的向量，原文区记录原文，metadata区便于搜索时过滤和溯源

>[!info] 切分粒度及策略

既然要切，那么每块大小多大？
- chunk 太大，向量把太多语义压缩在一起，变得笼统，检索时容易召回和问题只有部分相关的内容，同时也更容易超出 Embedding 模型的输入长度限制。
- chunk 太小，单个 chunk 语义不完整，上下文丢失，LLM 拿到这段内容也看不懂，而且检索噪音更多。

通常 500～1000 token 是合理的起点，但具体该怎么切呢？

**策略1：固定大小切割**
最简单的方式，按固定字符数或 token 数切割，不管语义边界在哪。优点是实现简单、chunk 大小可控；缺点是可能在句子中间截断，破坏语义完整性。

优化：==重叠==，缓解边界截断问题
因为按固定大小切割，容易将一句话切成两半，那么可以再选一个合适大小作为重叠区域，即使一个chunk切断了一句话，这句话也会出现在另一个chunk里。
![[Pasted image 20260521213829.png]]
**策略2：语义边界切割**
按文档的自然语义边界来切，比如段落、句子、标题层级。核心思想是：不要在语义中间截断，找到文字天然的「断点」再切。

实际操作时，常见的做法是维护一个分隔符优先级列表，先尝试按段落切，切出来太大再按句子切，还是太大再按标点切，以此类推，直到满足 chunk_size 限制。
![[Pasted image 20260521214015.png|376]]
对于有标题的HTML,Markdown文件，还可以按标题分

**策略3：特殊内容专项处理**
前面两种策略对普通文本够用了，但遇到代码文件和表格就会露馅，通用切割策略在这两种内容上效果很差，需要单独处理。
对于代码：一个类，一个函数等不要在内部进行切分。
对于表格：表格则要整块保留，转成 Markdown 格式存储，不能按行截断。

**策略4：父子切分**
固定大小可能切断语义，语义边界切割质量好但粒度不好控制，你自然会问：有没有一种策略能同时兼顾检索精度和上下文完整？
核心思路可以用一句话概括：检索时用放大镜（小块，精准定位），返回时用全景图（大块，上下文完整）。

存储时，同一段内容存两份。一份是细粒度的==小 chunk==（比如 200 token），专门用于==向量检索==，因为小 chunk 语义聚焦，围绕一个小话题，检索精度高。另一份是包含这个小 chunk 前后上下文的大 chunk（比如 1000 token），通过 ID 与对应的小 chunk 关联。检索时用小 chunk 找到精准的命中点，然后根据关联 ID 取出对应的==大 chunk==，把完整的上下文交==给 LLM 阅读==，生成质量更好。


**策略5：Late Chunking**
先把整篇文档丢给一个支持长上下文的 Embedding 模型，让模型做一次完整的前向传播，输出文档里每个 token 的向量（这些 token 向量之间已经通过注意力机制彼此感知过了）；然后按照 chunk 的边界，把落在同一个 chunk 里的所有 token 向量做 mean pooling，得到这个 chunk 最终的向量。

#### 2.1.3Embedding

>[!info] Embedding是什么

Embedding翻译过来是嵌入的意思，在RAG中embedding是将一段文本转化成向量，这些向量有个特性：语义相近的文本，转出来的向量在数学空间里的距离也近。这就和嵌入很像，将文本嵌入到向量当中，搜索时与搜索文本向量相近的向量，就能找到意思相近的文本。

>[!info] embedding算法

**第一代算法：word2vec...**
它们的核心思路非常朴素：用一个词周围的词来预测这个词，或者反过来用这个词来预测周围的词。通过大量文本训练，语义相近的词自然就会在向量空间里被推到一起。
![[Pasted image 20260522191353.png]]
缺点如图：每个词的向量固定，无法区分多义词

**第二代算法：ELMo，BERT**
理解了第一代「一个词永远只有一个向量」的局限，第二代算法的改进方向就很明确了：让词的向量随上下文动态变化，同一个词在不同句子里有不同的向量表示。

ELMo：用双向 LSTM 来建模，从左向右扫一次，从右向左扫一次将两个方向的状态作为词的上下文向量

BERT：改用Transformer，并引入了 Masked Language Model（随机遮盖句子中 15% 的词，让模型根据上下文预测被遮盖的词，迫使模型同时学习**上文和下文的信息**） 预训练任务，真正看到了上下文。

**BERT缺点：**
BERT 用 [CLS] token 来表示整个句子（CLS是句子开头标记，BERT 处理句子时，每个词（包括 `[CLS]`）都会经过多层 Transformer 编码器，生成一个对应的向量。而 `[CLS]` 经过所有层计算后得到的最终向量，会被模型 “浓缩” 了**整个句子的上下文信息**，可以直接用来代表这个句子的整体语义。）
要比较两个句子的相似度，必须把两个句子拼在一起喂给 BERT（Cross-encoder），让 [CLS] 来做判断。百万级数据库根本无法使用

**第三代算法：句子级对比学习**
第二代 BERT 虽然语义理解能力强，但「必须两两拼接」这个限制让它在检索场景下完全没法用，这就引出了第三代的核心理念：能不能让每个句子独立生成一个向量，然后直接用余弦相似度来比较？

解决方法是用 bi-encoder（将查询语句和知识库分别向量化） 独立编码，提前算好向量存起来，检索时只算余弦相似度，是 RAG 的标配。



#### 2.1.4存入向量数据库

>[!info] 什么是向量数据库，为什么要向量数据库

普通的数据库也能存向量，为什么还专门需要向量数据库呢？

RAG 场景里真正要解决的，不只是“能不能存 Embedding”，而是能不能在大规模高维向量里，低延迟找出==最相关==的 Top-K。

传统关系型数据库可以存向量，也可以通过函数或 SQL 表达式计算相似度。但如果没有专门的向量索引，通常只能全表扫描，很难支撑生产级低延迟检索。

而向量数据库，就是专门存储和检索向量的数据库。

>[!info] 向量索引算法

![[Pasted image 20260522194315.png]]
ENN使用于低维（如1维，即普通数据库）
但向量检索要做的事完全不同——不是找「等于」的，而是找「最相近」的，没有精确匹配，只有相似度排序。
所以我们在谈向量索引，一般谈的是ANN（近似最近邻搜索）。

**HNSW（图索引算法）**
这是目前召回率最高的 ANN 算法之一。它把向量组织成多层网络图，查询时像导航一样在图上走。HNSW 通常能在查询速度和召回率之间取得比较好的平衡，缺点是建索引时内存消耗大，不适合内存极度受限的场景。是目前综合表现很强的一类算法。
![[Pasted image 20260522194906.png]]
**IVF：基于量化的算法**
它先对向量做聚类，把相似的向量分进同一个「桶」里，查询时只搜最相关的几个桶，而不是全量遍历。缺点是精度比 HNSW 略低，需要调参（聚类数量 nlist、搜索桶数量 nprobe）。Milvus 在超大规模场景下会用 IVF 系列索引。

![[Pasted image 20260522195047.png]]
>[!info] 向量检索和关键词检索的区别

关键词检索的代表是 BM25（Best Match 25）
核心思想是：根据词频和文档频率给每个词打分，找出包含查询词最多、且这些词在整个语料里不太常见（也就是区分度高）的文档。
优势对**精确词汇命中率极高**，但无法搜索出同义词。

而这缺点正是向量数据库优势，
向量检索靠语义空间距离，语义理解强，**但对精确词汇不敏感**，人名，版本号这类词，向量检索容易混淆。

工程实践中的标准做法叫混合检索（Hybrid Search）：同时跑向量检索和 BM25，各自召回一批候选，然后用 RRF（Reciprocal Rank Fusion，互倒排名融合）算法把两路结果合并排序。

RRF 的思路很巧妙：它不看各路的原始分数，只看排名。你可能会问，为什么不直接把两路的分数加权平均呢？原因是向量相似度（0 到 1 的余弦值）和 BM25 分数（可能是任意正数）的量纲完全不同，RRF 用排名的倒数来打分，排名越靠前倒数越大，最终按总分降序排列。这样，两路都认为相关的文档会排在最前面，只有一路认为相关的文档也不会被完全丢掉。

![[Pasted image 20260522204011.png]]
并且，关键词索引和向量索引是并行执行的，几乎没有额外的时间代价，但召回质量比单路明显更好。

### 2.2在线检索
![[Pasted image 20260522200328.png]]
#### 2.2.1Query 处理。
用户的提问往往是口语化的，或者比较模糊，直接拿去检索效果不一定好。
- 比如用户问「上次说的那个方案怎么样」，这个问题离开对话上下文完全没法检索，因为检索系统根本不知道「上次」指的是什么、「那个方案」又是哪个。
- 所以实际工程里会加一步 Query 改写，让 LLM 把用户的问题改写成更适合检索的形式，或者从对话历史里补充必要的上下文。

>[!info] query处理有哪些方法

**1.直接改写**
将用户问题和上下文发给另一个llm，由另一个llm改写，解决口语化和指代不清的问题。

但还有另一种鸿沟是改写搞不定的，问题和文档本来就是不同的文体，一个是疑问句，一个是陈述句，就算你把问题改写得再规范，它在向量空间里还是「问句」的坐标，而文档是「陈述句」的坐标，两类文体之间天然有距离。

**2.HyDE（Hypothetical Document Embedding）**
Hypothetical:假设性
HyDE 的直觉可以这样理解：正常你用问题的影子去找答案的样子，HyDE 先描绘出答案可能长什么样子，再去找长得像它的文档。先让 LLM 根据用户问题生成一段「假设性的答案」，再用这段假设答案的向量去检索文档。假设答案不需要准确，只需要「风格像文档」就够了，它的作用是充当一个向量上更好的「检索代理」。

HyDE 解决的是「文体差异」的问题，但还有一类情况是 HyDE 和直接改写都处理不好的——用户的问题太具体了，知识库里压根没有直接对应的答案，但有相关的背景原理文档。这种情况下，不管你怎么改写、怎么假设，都很难从具体问题直接跳到背景知识。于是就有了 Step-back Prompting。

**3.Step-back Prompting**

对于涉及具体细节的问题，有时候知识库里没有直接对应的答案，但有背景原理。Step-back Prompting 把具体问题「后退一步」，提升到更抽象的层次，先检索背景知识，再结合背景知识回答具体问题。

让LLM将用户问题转化成一个更通用的问题，再根据新生成的通用问题检索

前面三种方法都是在「一个问题」上做文章——要么改写它、要么给它配一个假设答案、要么把它抽象化。但有时候问题的角度本身就比较窄，用一个角度去检索，覆盖面不够。这时候就需要换个思路：不求一个问题改得更好，而是多生成几个不同角度的问题。

**4.多query扩展**
用 LLM 把用户原始问题改写成 3～5 个不同角度的版本，分别去检索，然后把所有结果合并去重。核心思路是：只要有一个改写版本和文档的表述对上了，就能把正确的内容召回来，就像拦截网越宽，捕到鱼的概率越高。适合用户提问风格多变、和文档表述差异大的场景，代价是多几次 LLM 调用。



#### 2.2.2向量检索（粗排）
把用户的问题也转成向量，然后去向量库里做相似度搜索，找出向量距离最近的 ==Top-K== 个 chunk。
- 这一步速度非常快，即使是百万量级的向量库，通常也能在几十毫秒内返回结果。
- 但速度快是有代价的，向量检索本质上只是比较两个向量的距离，它没有深度理解查询和文档之间的语义关系，所以召回的结果里难免混入一些「看着近但其实不相关」的内容。

>[!info] 多路召回

多路召回，顾名思义，就是同时用多种不同的检索方式去捞候选内容，最后再把各路结果合并、排序，交给 LLM 生成答案。

![[Pasted image 20260522205443.png]]

为什么要向量检索+BM25见[[agent#2.1.4存入向量数据库]]向量检索和关键词搜索区别部分。
简单来说就是向量检索解决了关键词搜索对同义词命中率低的缺点，关键词搜索弥补了向量检索对精确词语命中率低的缺点。而多query扩展则扩展了回答的角度

**选哪几路？**
知识库大量名词：向量检索+BM25
用户提问方式多变（如电商客服）：+多query查询

#### 2.2.3Rerank（精排）。
这一步就是为了弥补粗排的不足。
- Rerank 模型（通常是 Cross-Encoder 结构）会把用户问题和每个候选 chunk 拼在一起，深度理解它们之间的相关性，然后重新排序，把不相关的结果过滤掉。
- 打个比方，粗排就像你用肉眼在书架上快速扫了一遍，把看着可能相关的书都抽了出来；精排就是你一本一本翻开读目录，确认哪些书真正有用。精排更准但更慢，所以通常只对粗排返回的 Top-20 结果做精排，最终留下 Top-3 到 Top-5。

>[!info] 为什么需要Rerank，把找出来的文档全部塞给llm不就完啦？

多路召回之后，候选 chunk 可能有 20~30 个，这些 chunk 里难免混入一些不太相关的内容，直接全塞给 LLM 会出问题：
- 一是 token 消耗暴涨，成本直线上升；
- 二是上下文太长，LLM 在处理长文本时容易出现「Lost in the Middle」的现象，也就是只关注开头和结尾，中间的内容容易被忽略。
![[Pasted image 20260522210811.png]]

>[!info] 向量检索不是重排过了吗，Rerank是怎么重排的？

向量检索用的是 ==Bi-encoder== 结构：query 和 chunk ==各自独立编码成向量，再算余弦相似度==。这个结构的优点是速度极快，因为 chunk 的向量可以提前计算好存库，检索时只要算一次 query 的向量然后做距离比较就行；缺点是 query 和 chunk 是分开编码的，模型没办法看到两段文字之间的具体词语关联，相关性判断不够精准。

Rerank 用的是 ==Cross-encoder== 结构，把==「query + chunk」拼成一对输入==，让模型整体看这一对的相关性。Cross-encoder 能看到 query 中每个词对 chunk 的影响、chunk 里哪些词最能回答 query，相关性判断精度远高于 Bi-encoder。代价是每一个候选 chunk 都要单独跑一次 Cross-encoder，速度慢，所以只适合对小规模候选集做精排，不适合大规模召回阶段。

Rerank 的流程很清晰：多路召回得到 20~30 个候选 chunk，Cross-encoder Rerank 模型逐一给每个「(query, chunk)」对打相关度分，按分数降序排列后，取 top-3 到 top-5 拼入 prompt。

#### 2.2.4生成
把用户问题 + 精排后的 chunk 拼成 prompt，交给 LLM 生成最终答案。
- Prompt 里通常会明确告诉 LLM「只根据提供的资料回答，资料里没有就说不知道」，这样能有效抑制 LLM 瞎编的倾向。

## 3.RAG范式

### 1.为什么需要不同RAG范式
「范式」这个词听起来很学术，其实就是「一套固定的处理流程和设计思路」。RAG 范式，就是指从「用户提问」到「生成答案」这整条链路上，各个环节的组织方式和工作逻辑。

最开始的RAG范式是Naive RAG：朴素RAG
它的流程为：提问->检索->拼prompt->回答
具有以下三个问题：

第一个问题是==检索质量参差不齐==。用户的提问方式千变万化，有些问题一次检索就能找到正确答案，有些问题向量检索完全召不到相关内容，但==系统不会区分==，一律把检索结果喂给 LLM。然后呢？LLM 就会在低质量上下文上胡说八道，而用户完全不知道答案有没有依据。

第二个问题是所有问题都走同一套流程，==太死板==。有些问题根本不需要检索，比如「你好」「今天天气怎么样」，强行去知识库里找毫无意义；有些复杂问题需要多轮检索才能拼出完整答案，而朴素 RAG 一律只检索一次。然后呢？该省的地方没省，该深挖的地方浅尝辄止，结果既浪费又不准。

第三个问题是知识库覆盖==有盲区==。知识库里永远不可能有所有答案，当找不到相关内容时，朴素 RAG 要么让 LLM 编造答案，要么返回一个风马牛不相及的回答。然后呢？用户拿到的是一个自信满满的错误答案，体验很差。

这三个问题，催生了不同思路的 RAG 范式：有的在「如何检索」上做文章，有的在「要不要检索」上加判断，有的在「检索不到时怎么兜底」上下功夫。理解这些范式，本质上是理解面对不同场景约束时，系统设计者各自找到的解法。

![[Pasted image 20260522212750.png]]

为了解决检索质量差的问题，Advanced RAG诞生了。具体流程就是上面提到的在线检索[[agent#2.2在线检索]]，核心思路是在检索前将query改写，检索后rerank重排序选最佳。但advanced rag仍没有解决太死板的问题。

再往后发展就是 Modular RAG，思路变了，不再是在固定流程上打补丁，而是把 RAG 的各个环节拆成可以独立替换的模块，像乐高一样按需组合：检索模块可以选向量检索、BM25 或图检索；改写模块可以选 HyDE、Step-back 或多 Query 扩展；生成模块可以是普通输出，也可以是带引用的结构化输出。

### 2.Modular RAG范式(高级范式)
Modular RAG的实现有多种范式。
#### 2.1Self-RAG
前面提到朴素 RAG 的第二个痛点是「所有问题都走同一套流程，太死板」。Self-RAG 就是专门解决这个问题的。
![[Pasted image 20260522213746.png|504]]
self-rag有一个或多个llm配合完成以下五步
1. 评估问题是否需要检索，不需要则直接让回答问题llm生成答案，需要则继续检索
2. 召回多个chunk
3. 判断召回chunk相关性：不相关则舍弃，相关的进入下一步
4. 每一个chunk生成一个候选答案
5. 评估答案质量：对每个候选答案，LLM 打两个分，有没有文档支撑（防幻觉）、答案对用户有没有用。
6. 选出最优答案返回：综合两个分数，选出最好的那个候选答案。

优点是解决了Naive RAG太死板的问题以及检索不到的问题
缺点是self-rag的llm需要经过微调才能使用。

#### 2.2CRAG（Corrective RAG）：检索质量差时自动纠错
Self-RAG 解决的是「要不要检索」的问题，那如果检索了但结果质量很差怎么办？

朴素 RAG 的第三个痛点：知识库覆盖有盲区。就会导致这种情况。CRAG 就是专门解决这个问题的。

CRAG 在检索完之后加了一个质量评估环节：如果检索到的内容质量高，正常走 RAG 流程；如果质量低，自动切换到网络搜索，用搜索结果代替知识库内容来回答问题；如果质量居中，把知识库结果和网络搜索结果都用上。
![[Pasted image 20260522214601.png]]
这个方案的核心价值在于「兜底」：知识库覆盖不到的问题不会直接乱答，而是自动去网上找答案，大幅提升了系统的健壮性。很多人以为 RAG 系统只能用本地知识库回答问题，CRAG 打破了这个限制，它把知识库当主力，把网络搜索当备胎，两者配合使用。

#### 2.3GraphRAG
Self-RAG 和 CRAG 解决的都是「检索策略」层面的问题，但还有一种瓶颈是检索方式本身的局限。

普通向量检索只能召回「和问题直接相关的文档片段」，对于需要全局理解的问题（比如「这批文档的核心主题是什么」「A 公司和 B 公司之间有什么关联」），单纯的向量检索只能找到局部信息，无法把散落在多处的知识串联起来。

GraphRAG核心做法分两步，一步是预处理阶段，一步是检索阶段。

>[!info] 预处理阶段

![[Pasted image 20260522215741.png]]
它比其他RAG多了：
- 实体抽取：识别文档里的系统、人、组织、概念、事件
- 关系抽取：识别实体之间的依赖、包含、影响、因果等关系
- 图谱归一：合并重复实体，补充属性和来源（成本高，需要人工评测）
- 社区发现：用Leiden 等社区发现算法对图谱中的实体做聚类，把紧密关联的实体分成一个个「社区」
- 摘要生成：对每个社区生成一份 LLM 摘要，描述这个社区里的实体之间是什么关系、整体在讲什么。这些社区摘要会形成多层的层次结构，从细粒度到粗粒度都有覆盖。
