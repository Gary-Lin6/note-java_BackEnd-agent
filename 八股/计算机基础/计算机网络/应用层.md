# 一.基本概念
## 1.协议分层
对于同一台设备上的进程间通信，有很多种方式，比如有管道、消息队列、共享内存、信号等方式，而对于不同设备上的进程间通信，就需要网络通信，而设备是多样性的，所以要兼容多种多样的设备，就协商出了一套通用的网络协议。

这份协议是分层的，分为应用层，运输层，网络层，链路层，物理层。

分层使网络概念化和结构化，让开发者专心与自己该层的开发。

## 2.应用体系结构
### 2.1客户-服务器体系结构
- 有一个总是打开的主机：服务器。它服务许多其他主机：客户的请求。
- 客户相互之间不直接通信。
- 服务器具有固定，周知的地址：IP地址

### 2.2P2P体系结构
- 应用程序在间断连接的主机（对等方）之间使用直接通信

对于P2P体系结构，可以理解双方即为客户又为服务器。
## 3.报文
应用程序之间相互通信，其实是进程间相互通信。
当多个进程在同一个端系统间上，它们使用进程间通信机制相互通信，比如有管道、消息队列、共享内存、信号。通信机制由操作系统决定。
而在两个不同端系统上的进程，要进行通信，要发送的信息，叫做**报文**。

# 二.应用层协议
既然知道，在两个不同端系统上的进程要通过报文来通信。那么就需要规范如何构造报文，报文各部分内容是什么，何时发送报文等问题。否则，不同端的进程发送的报文含义不同，根本无法进行交流。因此应用层协议是非常有必要的。

>[!info] 应用层协议与网络应用的关系

应用层协议是应用的一部分。应用除了能解决业务需求外，还要指定应用层协议是什么，以便于应用之间的交流。
（从指定这句话也能看出，应用层协议其实有多种，不同应用对应不同协议。这里介绍几种最常见的）

## 1.HTTP
### 1.1什么是HTTP
HTTP 是超文本传输协议，也就是**H**yperText **T**ransfer **P**rotocol。
它是Web（Web应用体系结构是客户-服务器结构）的应用层协议。

**超文本是什么**
互联网中，除了文字，还有图片，视频等，把这些总和在一起，叫超文本。

### 1.3cookie
#### 1.3.1为什么要cookie：HTTP是无状态协议。
**什么是无状态协议：**
根据对HTTP报文的观察，HTTP报文并没有强制存储任何关于请求用户的信息。这使得某用户在同一时间向服务器请求同一对象，服务器并不知道这是同一个客户，而是重新发送对象。
因此，我们称HTTP是无状态协议。

**为什么要cookie：**
但有的网络应用，希望能够识别用户（比如你登录时也不希望每次刷新都要重新登录一遍吧）。
cookie就是为了解决这一问题而生的。

#### 1.3.2cookie是怎么解决无状态协议的
**cookie长什么样：**
cookie由四部分组成：
- HTTP响应报文的首部行有 cookie： ...
- HTTP请求报文的首部行有cookie： ...
- 用户端系统中保留一个cookie文件，并由浏览器保管
- Web站点有个后端数据库。

**cookie工作全流程：**
用户第一次访问某个网站时：
- 用户正常发送HTTP请求报文。
- 服务器会为用户创建一个id，并在后端数据库添加该用户，记录其在该服务器访问了什么等等。
- 随后返回一个HTTP响应报文，其中首部行有一行Set-cookie： id
- 浏览器收到响应报文后，除了解析内容外，还会在本地cookie文件加一行：cookie： id
用户接下来访问该网站：
- 浏览器会在请求报文中带上前面记录的cookie： id
- 浏览器收到其cookie后，在后端数据库查找，返回对应id的内容。

这样cookie在无状态HTTP上建立了用户会话层，实现了服务器识别用户的要求。

### 1.4不同版本的HTTP协议
#### 1.4.1HTTP/1.0
HTTP/1.0是HTTP最开始的版本，它最大特点是非持续连接。

>[!info] 非持续连接与持续连接

Web运输层协议是TCP，每个选用TCP的应用都要做出决定：
- 每个请求/响应都经不同的TCP连接发送（非连续连接）
- 每个请求/响应都经同一个TCP连接发送（持续连接）
下一章我们会知道TCP连接是怎么样的，这里我们只用知道每次建立和取消TCP连接都比较花费时间即可。

HTTP/1.0是非持续连接，这就导致，有N个文件就要建立N次TCP连接，相当耗费时间。
虽然可以用并行连接缩短时间，但还是不如持续时间更高效。

#### 1.4.2HTTP/1.1
为解决HTTP/1.0非持续连接问题，HTTP/1.1诞生了。
主要的解决思路是，使用同一个 TCP 连接来发送和接收多个 HTTP 请求/应答，避免了连接建立和释放的开销，这个方法称为 HTTP 长连接。
![[Pasted image 20260526162533.png]]
解决办法就是：在请求和响应报文的首部行加Connection： Keep-Alive。
告诉对方，建立完连接后不要急着断开。

怎么断开：
- 设置keepalive_timeout参数，多少s后没http请求主动断开。
- 主动断开：Connection： Close

>[!info] **HTTP 流水线**技术

所谓的 HTTP 流水线，是客户端可以先一次性发送多个请求，而在发送过程中不需先等待服务器的回应，可以减少整体的响应时间。

举例来说，客户端需要请求两个资源。以前的做法是，在同一个 TCP 连接里面，先发送 A 请求，然后等待服务器做出回应，收到后再发出 B 请求。HTTP 流水线机制则允许客户端同时发出 A 请求和 B 请求。
![[Pasted image 20260526162801.png|462]]
但是服务器还是按照顺序响应，先回应 A 请求，完成后再回应 B 请求。

而且要等服务器响应完客户端第一批发送的请求后，客户端才能发出下一批的请求，也就说如果服务器响应的过程发生了阻塞，那么客户端就无法发出下一批的请求，此时就造成了「队首阻塞」(HOL)的问题。

>[!Info] 什么是队首阻塞（HOL）问题

前面提到服务器是按顺序响应，如果先传回的数据很大，需要很长时间才能传回去。而队尾文件都很小，很快就能传完。但因为服务器要按顺序传文件，导致队尾的文件一直传输不了，造成阻塞。

当然HTTP/1.1也有解决方案，就是并行开多条TCP连接来传输文件。但太多的HTTP连接对服务器来说是个负担。因此HTTP/2的主要目标就是只用1个TCP连接来解决HOL问题。

#### 1.4.3HTTP/2

>[!info] 解决HOL

HTTP/2解决HOL阻塞的解决方案是把每个报文拆分成小帧。
当服务器要发送一个HTTP响应时，成帧子层会将响应划分为帧并进行二进制编码（首部字段一帧，报文体若干帧...)（原本HTTP报文头是ASCLL码形式，占用空间大且不易解析，二进制编码后占用空间更新且更易解析）
随后不同响应报文的帧交错经过单一TCP发送到客户，到达客户后，客户的成帧子层先把同一个响应报文的帧组装并解析成原始报文，接着给浏览器解析。
同样的，HTTP请求也拆分成帧发给服务器。

通过拆分成小帧交错发送。可以解决HOL问题。
例如一个大视频1000帧，9小视频各2帧。
按HTTP/1.1的方式发送，小视频得等1000帧后才能发。
而按交错发放帧的方式，20帧后，小视频就发完了。
极大减少了用户的感知延迟。

>[!info] 头部压缩

HTTP 协议的报文是由「Header + Body」构成的，对于 Body 部分，HTTP/1.1 协议可以使用头字段 「Content-Encoding」指定 Body 的压缩方式，比如用 gzip 压缩，这样可以节约带宽，但报文中的另外一部分 Header，是没有针对它的优化手段。

HTTP/1.1 报文中 Header 部分存在的问题：

- 含很多固定的字段，比如 Cookie、User Agent、Accept 等，这些字段加起来也高达几百字节甚至上千字节，所以有必要压缩；
- 大量的请求和响应的报文里有很多字段值都是重复的，这样会使得大量带宽被这些冗余的数据占用了，所以有必须要避免重复性；
- 字段是 ASCII 编码的，虽然易于人类观察，但效率低，所以有必要改成二进制编码；

HTTP/2使用 **HPACK** 算法进行压缩，HPACK 算法主要包含三个组成部分：
- 静态字典；
- 动态字典；
- Huffman 编码（压缩算法）；

客户端和服务器两端都会建立和维护「字典」，用长度较小的索引号表示重复的字符串，再用 Huffman 编码压缩数据，可达到 50%~90% 的高压缩率。

**静态表**
在统计大量的 HTTP 头部后，HTTP/2 根据出现频率将 ASCII 码编码为了 Huffman 编码表，这样可以用更少的bit表示常见的字符。

**动态表**
静态表只包含了 61 种高频出现在头部的字符串，不在静态表范围内的头部字符串就要自行构建动态表，它的 Index 从 62 起步，会在编码解码的时候随时更新。
在第一次发送报文遇到没遇过的字符串，则通知双方更新动态表，下次再遇到这个字段，就可以用动态表里的编码来压缩。

>[!info] 报文优先次序

HTTP/1.1回复的报文得按顺序回复。但有了成帧技术，可以给想要的报文优先级提高，优先级越高，发送帧的次序越靠前，实现报文优先次序。

>[!info] 服务器主动推送资源

HTTP/1.1 不支持服务器主动推送资源给客户端，都是由客户端向服务器发起请求后，才能获取到服务器响应的资源。

比如，客户端通过 HTTP/1.1 请求从服务器那获取到了 HTML 文件，而 HTML 可能还需要依赖 CSS 来渲染页面，这时客户端还要再发起获取 CSS 文件的请求，需要两次消息往返，
![[Pasted image 20260526170704.png]]
在 HTTP/2 中，客户端在访问 HTML 时，服务器可以直接主动推送 CSS 文件，减少了消息传递的次数。

### 1.6Web缓存
对于同一片区域的人，一些具有重复性的 HTTP 请求，比如每次请求得到的数据都一样的。我们可以用一台Web缓存器（代理服务器）来缓存请求到的数据，以加快请求-响应速度。

#### 1.6.1有Web缓存器后请求过程

1. 浏览器与Web缓存器创建一个TCP连接，并发送一个HTTP请求
2. 缓存器检查本地是否存储了该对象副本。
	- 如果有，则直接返回。
	- 如果没有，则Web缓存器与原本的服务器建立一个TCP连接，并发送请求该对象的HTTP请求。收到请求后，服务器向缓存器返回该对象。
3. Web缓存器收到该对象后，在本地缓存该数据，并向浏览器返回响应。
4. 下次再请求同一个对象时，Web缓存器可以直接返回该对象，缩短响应时间。

#### 1.6.2如何保证缓存一致性？

有了缓存后随即带来了个新问题。缓存器上的数据可能是旧的，怎么保证缓存上的数据与服务器上的数据是一致的？

有两种方法实现：
**强制缓存（书上没提，这里学来的[强制缓存](https://xiaolincoding.com/network/2_http/http_interview.html#http-%E7%BC%93%E5%AD%98%E6%9C%89%E5%93%AA%E4%BA%9B%E5%AE%9E%E7%8E%B0%E6%96%B9%E5%BC%8F)）**
强缓存指的是只要Web缓存器判断缓存没有过期，则直接使用Web缓存器的本地缓存，决定是否使用缓存的主动性在于缓存器这边。

具体实现是Web缓存器还没有数据时，向服务器请求数据，服务器的响应报文可能有以下两个字段：
- `Cache-Control`， 是一个相对时间；
- `Expires`，是一个绝对时间；它们设置了返回资源的过期时间。
相当于告诉了Web缓存器，这段时间内，我不会更新的，放心大胆用。

于是，当用户向Web缓存器申请资源时，Web缓存器发现该资源有这两个字段，并且还没有过期，就可以直接返回资源，而不用担心缓存一致性问题。

**协商缓存**
协商缓存是Web缓存器在收到用户申请，即使本地有缓存，还要向服务器询问：过期了吗？如果过期了就获取新数据，没过期就用本地数据。

具体实现是：在缓存器第一次向服务器请求数据时，服务器返回的响应报文的首部行可能有以下两个字段:
- `Last-Modified：...`，它表示该资源最近被改动的时间
- `Etag`,资源的唯一标识，不同资源（包括同一资源改动，Etag不同）
缓存器不仅接受了返回的对象，还记录了该对象Last-Modified/Etag属性。

当下次用户再向Web缓存器申请资源时，Web缓存器会向服务器发送一个条件Get请求，其中首部行可能有以下两个字段：
- `If-Modified-Since:...(返回的Last-Modified)`，服务器将本地的修改时间与请求的修改时间比较，如果本地修改时间比请求修改时间更晚，说明已修改，正常返回对象。反之，说明没修改，则返回状态码和短语 304 Not Modified，不返回对象。告诉缓存器可以直接使用缓存对象
- `If-None-Match:...(Etag)`:服务器收到请求后进行比对，如果资源没有变化返回 304，如果资源变化了返回 200。

于是，缓存器就可以知道对象有没有更新，来保证缓存一致性。

>[!info] 协商缓存不是还要向浏览器发请求吗？快在哪？

快在发的是条件Get请求，如果没变不用返回对象，节省了带宽。

>[!info] 为什么有Last-Modified还要有Etag

这是因为 ETag 主要能解决 Last-Modified 几个比较难以解决的问题：

- 在==没有修改文件内容==情况下文件的最后修改时间可能也会改变，这会导致客户端认为这文件被改动了，从而重新请求；
- 可能有些文件是在==秒级==以内修改的，If-Modified-Since 能检查到的粒度是秒级的，使用 Etag就能够保证这种需求下客户端在 1 秒内能刷新多次；
- 有些==服务器==不能精确获取文件的最后修改时间。

因此实际上Etag优先级比Last-Modified高

## 2.SMTP
### 2.1什么是SMTP
SMTP：Simple Mail Transfer Protocol，简单邮件传输协议。
它是电子邮件的应用层协议。

### 2.2邮件传输过程
**两种角色**
user agent：用户代理，发送接收邮件要通过用户代理实现
mail server：邮件服务器。邮件服务器里有邮件队列和user agent的邮箱

**三步流程**
假设A要向B发一封邮件
1. A调用邮件代理程序，提供B邮箱地址和邮件，指示A user agent发送该邮件（SMTP格式）到A mail server的邮件队列中
2. A mail server 发现了邮件队列中A的邮件，于是尝试与B mail server 进行TCP连接（邮件传输是TCP），假设连接成功，则将邮件以SMTP形式发送给B mail server。连接不成功则进行重试等操作
3. B mail server接受到请求后，将邮件分发给B 邮箱。B想阅读邮件时，通过B user agent来获取B邮箱里的邮件（POP,IMAP,HTTP形式）。

	- From：寄信人
	- To：收信人
	- Subject：标题
中间以空白行隔开
- 报文体：正文部分

## 3.FTP
### 3.1什么是FTP
FTP：File Transfer Protocol
是一种经典的**文件传输协议**，实现在**异构操作系统 / 文件系统之间**（比如 Windows ↔ Linux、macOS ↔ 服务器），实现文件的双向传输。

### 3.2控制连接与数据连接
FTP 最独特的设计，就是使用两条独立的 TCP 连接，把 “指令对话” 和 “数据传输” 彻底分开，互不干扰。
控制连接：21端口，发送命令，持续连接。
数据连接：20（主动连接）随机（被动模式），传输文件，文件传输时建立，传输结束后取消。

### 3.3两种数据传输模式
**主动模式（PORT 模式）**
服务端向客户端传数据
    1. 客户端先和服务器的端口 21 建立控制连接。
    2. 客户端随机开启一个大于 1024 的端口`N`，并通过`PORT`命令告诉服务器：“我用端口`N+1`监听数据连接，你来找我。”
    3. 服务器用自己的端口`20`（数据端口），主动连接客户端的`N+1`端口，建立数据连接。

**被动模式（PASV 模式）**
客户端向服务端发数据
1. 客户端和服务器的端口 21 建立控制连接。
2. 客户端发送PASV命令，请求被动模式。
3. 服务器随机开启一个大于 1024 的端口P，并通过控制连接告诉客户端：“我在端口P等着，你来找我。”
4. 客户端用自己的随机端口，主动连接服务器的端口P，建立数据连接。


# 三.DNS
前面我们提到Web发请求时根据URL来找到服务器。但实际上一台服务器的地址有两种方法标识：主机名和IP地址。前面我们在发URL时，一般用的是主机名，因为这方便人们阅读。但实际上，路由器更喜欢的是IP地址，所以在发送HTTP请求前，先要将主机名转换成IP地址，而这个工作是由DNS（Domain Name System）完成的

## 1.DNS架构
**DNS层次结构**
- 根DNS：最顶层的DNS，存储TLD DNS的IP地址
- 顶级域（TLD）DNS：有.com DNS,.org DNS,.edu DNS等。存储权威DNS IP地址
- 权威DNS服务器：存储要找的服务器的IP地址
![[Pasted image 20260527162623.png|564]]

**本地DNS**
每个ISP（Internet server provider，比如中国电信，移动等，也有二级，三级ISP，比如小区宽带提供商）都有一台本地DNS，当主机通过ISP上网，就可以知道对应的DNS的IP地址。本地DNS存储着根域DNS IP地址

## 2.DNS工作流程(无缓存版)
比如查询www.server.com

1.客户端首先会发出一个 DNS 请求，问 www.server.com 的 IP 是啥，并发给本地 DNS 服务器
2.本地DNS收到请求后向根DNS发出DNS请求，问 www.server.com 的 IP 是啥
3.根DNS收到请求后，发现后缀是.com，于是发送.com DNS的IP地址给本地DNS，让本地DNS再去com DNS再去问
4.本地DNS收到回复后，再去问com DNS， www.server.com 的 IP 是啥
5.（com）TLD DNS收到请求后，找到负责 www.server.com 区域的权威DNS IP地址，并发给本地DNS，让它去找权威DNS
6.本地DNS收到权威DNS IP后，去找权威DNS，问www.server.com 的 IP 是啥
7.权威DNS收到请求后，找到www.server.com对应的IP并返回，
8.本地DNS再将获取到的IP地址返回给客户端。

至此DNS解析过程就完成了。

## 3.DNS缓存
每次查询IP都要绕这么一大圈太麻烦了吧！实际上DNS具有缓存技术。
本地DNS会缓存最近查询的（主机，IP）对，甚至会缓存顶级域（TLD)DNS服务器的IP地址，从而跳过询问根地址的流程。

因为IP名的修改一般不频繁，所以本地DNS缓存过期时间一般设为2天

## 4.DNS记录与报文
**DNS记录**
记录主机名到DNS的映射：(Name,Value,Type,TTL)
TTL：缓存过期时间。
Name，Value意义取决于Type
Type=A，Name：主机名(bar.foo.com)，Value：IP地址
Type=NS，Name：域名（foo.com），Value：管理该域的权威DNS
Type=CHAME，NAME：主机别名。Value：规范主机名（一个IP地址可能有多个主机别名和一个规范主机名）
TYPE=MX,NAME:邮件服务器的主机别名。Value：规范主机名
