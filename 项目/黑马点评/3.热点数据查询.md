
# 一.缓存异常
[[3.Redis 缓存#一.缓存异常]]

## 1.缓存穿透
一般是有人故意去访问数据库里不存在的值，这样缓存永远命中不了，而是直接打到数据库里，对数据库造成很大压力

**解决方案**
1. 前端检验访问合法性，先把一些请求明显不合理的参数打回，避免直接查询
2. 缓存空值：如果某个请求访问数据库返回为空，那么我们也将空值缓存到缓存内，这样下次再访问这个空值，则会命中缓存。
	- 占用内存问题：设置ttl
3. 布隆过滤器：将数据库里的数据先用N个哈希函数映射到布隆过滤器中，在查询数据前先查布隆过滤器，这样一定不在数据库里的请求就会被立马驳回。虽然存在误判可能，但会将不可能请求大量削减。

本项目选用的是布隆过滤器解决缓存穿透问题：因为如果恶意攻击者仿造多个不同合理值来攻击数据库，那缓存空值方法将失效。具体实现是引入了redission的布隆过滤器，并设置了误判可能性为0.1%。
## 2.缓存雪崩
大量缓存同时过期或缓存服务宕机，造成用户访问时，大量请求同时打到数据库。

**解决方案**
对于大量缓存同时过期：
1. 随机设置过期时间
2. 设置互斥锁：只有一个请求到达数据库查数据
3. 后台线程及时更新：可以启动一个后台线程定时检测热点key存在情况，如果发现过期则让数据库更新缓存。

对于缓存服务宕机：
1. 服务熔断，当发现缓存服务宕机时，直接进行服务熔断，将请求全部驳回，避免访问数据库。
2. 构建高可用缓存服务:比如构建集群。

本项目选用互斥锁+随机设置缓存过期时间来解决缓存雪崩问题。因为实现起来相对简单。
## 3.缓存击穿
某个热点key过期，导致大量请求达到数据库。

**解决方案**
1. 互斥锁：一次只能有一个请求到达数据库查数据，其他请求等待锁释放后读取缓存数值
2. 逻辑过期：不设置过期时间，而是在value中加一个逻辑过期时间。当请求发现逻辑过期时，多个线程抢一把锁，抢到锁的线程开启一个后台线程来从数据库取新数据，别的（包括抢到锁的线程）都返回缓存旧数据。

本项目选用逻辑过期解决缓存击穿问题，并进行了测试：手动修改数据库让缓存与mysql不一致，并等逻辑过期后，用jmeter进行了5s 5000线程并发请求，查看日志可以发现只有一次查询数据库重建缓存的过程，**证明在高并发的场景下，没有让所有的请求打到数据库，成功使用逻辑过期方案解决缓存击穿问题**。


# 二.多级缓存
对于优惠卷秒杀的情形，我们采用redis判断购买资格，消息队列异步扣减库存和生成订单信息的方法。
对于热点数据查询，比如查商家信息等。这类情况往往比优惠卷秒杀的情况并发度更高，单单使用redis一级缓存可能扛不住。而对于查询热点数据这种读多写少的问题。所以我们想到用Caffeine+redis二级缓存的形式。
**Caffeine是什么**：
基于 Java 的高性能本地缓存库，命中率高、延迟低。
**为什么不用redis集群：**
对于100w并发请求，访问100个不同商户，确实能达到分散的效果
但对于100w并发请求，访问同一个商户，那么就算用集群，最终也是落在一个redis机上。
所以不行
**用户请求流程**
- 先从本地缓存中获取数据，如果本地缓存有数据则返回数据
- 否则从Redis缓存中获取数据。如果Redis缓存中有数据则更新本地缓存，然后将数据返回客户端
- 如果Redis缓存没有数据则去数据库查询数据，然后更新Redis缓存，接着再更新本地缓存，最后将数据返回给客户端

## 三.缓存数据一致性问题
[[3.Redis 缓存#二.缓存一致性]]
通过一通分析，我们可以直到，先更新数据库再删除redis缓存的策略再加上给缓存设置ttl的方式兜底基本是有效的。但对于多级缓存的策略，因为可能我们布置的服务有多台主机，删除多台主机的本地缓存不方便。
那么我想到的有三种方法：
1. 给一级缓存设置较短的过期时间，这样子，在一级缓存过期后，读到的数据还是新的数据，实现方便。
2. 使用消息队列，如果mysql发生更改，则发一条消息给消息队列，所有主机监听这个消息队列，一有通知则进行删除操作。
3. 使用Canal：Canal原理是mysql的主从同步，canal通过伪装自己成一个slave节点，通过监听主节点的bin log得知数据库发生哪些变化，然后就可以通知java客户端。

我们这里选用的是给一级缓存加较短过期时间，原因也是因为比较简单。
