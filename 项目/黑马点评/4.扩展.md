
# 一.未支付订单自动关单
## 1.使用Spring task自动关单
在优惠券下单后，用户如果超过一定时间内仍未支付，那此时需要关闭订单，并且释放库存。
而在订单数据库表的设计中，有一列是订单状态：分为已完成，未支付，已关闭。所有插入订单表的订单一开始状态均为未支付，支付完成后修改为已完成。还有一列是创建订单时间。
所以解决这个问题的关键，就是将未支付，且超时的订单状态改成已关闭，并新增库存。

这里我想到了三个方法：
1. 第一个很自然的方法：就是使用Spring task开启一个定时任务，每隔1分钟，去数据库查status=“未支付” and order_time<（当前时间-订单时长）
2. 利用消息队列的延迟消息，在订单创建时发送一条延迟消息，一段时间后，消费者获取到延迟消息后，检查订单是否支付。
3. 使用redis过期监听：我们可以将订单存在redis并设置一个过期时间。通过配置redis.conf开启过期监听，那么key过期时就能检测到并进行关单操作。

最终选用Spring task+扫描数据库的方法来解决这个问题。
原因如下：
1. 使用消息队列，大部分的消息可能都是无效的（即这些订单已支付），并且消息队列存在消息丢失和重复消费现象。不利于关单的正确性。
2. 使用redis过期监听，由于redis其实是惰性删除，所以过期时间于关单时间存在差异。
3. 虽然扫描数据库听起来很慢，但实际上，通过给（status，order_time)加上联合索引，就可以大大提高搜索效率。

并且我还设置了兜底方案：由于有时定时任务时间不够准确，用户可能在订单过期后查看订单。那么在查看订单前，我加了一个判断，检查订单是否超时，如果超时则直接返回订单已关闭，并同时修改订单状态，实现被动关单。

**采用扫描方式，会不会造成重复关单，从而使得库存额外增多**
mysql update操作会给这行加行级锁，再加上mysql一个操作就是一个事务，因此两者间会互斥。我们的sql操作是update set status="已取消" where status ="未支付"...,所以最多只能有一个sql语句修改status成功。那么也就只能执行一次库存修改。

**如果订单状态设置为关闭，但是库存增加失败怎么办？**
我采用的解决方法是利用消息队列重试机制，引入消息队列，异步增加库存。如果多次增加库存失败。则触发警告，让人工来解决。

## 2.关单和支付并发
现实还会遇到这种问题，用户在订单刚好过期的时候支付了，怎么办？

支付成功的回调 和 超时关单 在并发的场景下，都查询到订单的 状态为 "未支付"

此时后台对于 "支付成功的处理" 以及 "超时关单的处理"。这两者应当是一个成功，一个失败

所以要保证并发场景下一个成功、一个失败。我觉得有两种方案：
1. 乐观锁。支付和关单都要对数据库status进行更新操作。只要我们都是update status=”xx" where status="未支付"。那么只有一个操作能成功，就不会出现并发问题。为什么要加where status=“未支付”可以看[[3.MySQL锁#5.MySQL是怎么加行级锁的？]],加的锁其实是在索引上的。
2. 悲观锁：支付和关单抢同一把锁，然后进行修改。

显而易见，乐观锁性能更高。因此我选用乐观锁。

根据乐观锁避免了并发，其实就是"订单支付成功"和"订单超时取消"两种状态的“争夺”

此时就会出现两种情况：

**第一种情况："支付成功的回调" 处理成功，"超时关单" 处理失败**

- 这种情况很简单，"支付成功的回调" 处理成功，状态更新为“已支付”，"超时关单"必然处理失败，此时我们无需额外的处理，业务上是完全没有问题的。

**第二种情况："超时关单" 处理成功，"支付成功的回调" 处理失败**

- 这种情况就需要额外的处理了，因为"超时关单" 处理成功，状态更新为"取消"，而 "支付成功的回调" 处理失败，就是用户已经支付了钱，但是业务上支付却没有成功，订单却超时关闭了。这时候钱怎么办，所以这时候如果发现订单被关闭了，那么就需要触发原路退回的流程，把钱给用户退回。

**问题：第二种情况："超时关单" 处理成功，"支付成功的回调" 处理失败，为什么一定要退款，不能让订单变成 "已支付状态"吗？**
因为超时关单还伴随着库存的增加，如果让订单变成已支付状态，则库存会额外增多。


# 二.无库存订阅和到卷通知
在库存为0时，抢购按钮会变成订阅按钮，用户在订阅后，会根据用户级别，vip级永远比普通用户在前面，同级别用户按先后顺序排列。到卷后，根据到的库存量N，通知前N位用户。

对于存储订阅用户，我想到用redis的zset，只要维持好订阅用户的value，即可天然实现排序功能。
对于通知功能，我想到两个方法：
1. 启用Spring Task每隔一段时间查询库存是否有改变。如果有改变，则拉取redis前N个用户，进行通知操作。
2. 使用rocket mq信息队列，当补库存或者关单后库存增加，向消息队列发一条消息，消费者拿到消息后，拉取zset前N个用户发通知。
这里我选用第二种方法，因为补库存和关单并不常发生，如果专门设置一个Spring task的话会造成循环浪费。

## 1.value的设计
思路很简单，value=priority_base + join_timestamp。
如果是vip用户，priority_base=0,如果是普通用户，priority_base=一个很大的数比如10^14次方（毫秒级时间戳一般13位）。
join_timestamp当前时间戳。天然实现vip用户比普通用户在前。

## 2.储存订阅用户
用户点击订阅按钮后，用lua脚本，判断用户是否已经在订单里，是否已经订阅，如果都不是，则根据value设计规则，插入到zset内。

## 3.到卷通知
当库存发生改变时，向消息队列发一条消息。消费者收到后，尝试获取分布式锁（避免多个库存更改时间并行发消息，消费者同时收到两个消息，造成对前N个人的重复通知）
获取到分布式锁后。检查库存余量，如果余量== N，消费者用拉取zset前N个用户（并将其从zset里删除），并进行通知处理，同时在发一条延迟消息，5分钟后再让消费者检查库存。直至发现库存== 0，或zset为空。
