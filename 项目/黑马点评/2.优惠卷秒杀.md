# 一.优惠卷ID设计
优惠卷的ID不能使用自增ID实现：
1是因为如果使用自增ID，过于规律，可能暴露敏感信息
2是因为MySQL单表容量不宜超过500w，因此以后数据多后要进行分表，分表后id又是从1自增，ID重复，难以区分

于是我们选用雪花算法来进行ID的计算，ID为64Long型整数，各为含义如下
![[Pasted image 20260605193234.png]]
可以根据需求来改变各部分长度。

# 二.优惠卷超卖和一人一单
## 1.乐观锁解决优惠卷超卖问题
一开始，我们实现优惠卷秒杀功能的代码是这样的：
```java
 if (voucher.getStock() < 1) {
        // 库存不足
        return Result.fail("库存不足！");
    }
    //5，扣减库存
    boolean success = seckillVoucherService.update()
            .setSql("stock= stock -1")
            .eq("voucher_id", voucherId).update();
    if (!success) {
        //扣减库存
        return Result.fail("库存不足！");
    }
```
但这会造成如下问题：
![[Pasted image 20260605194119.png]]
库存 == 1时，线程1查到库存还没<1，刚准备扣库存，线程2来了，也判断库存未<1，于是直接扣了库存，这时线程1也扣了库存，导致超卖，即库存== -1了。

怎么解决？
这是很经典的线程冲突问题，常见的做法就是加锁。
加锁又可以加悲观锁和乐观锁。这里我们选用乐观锁。因为悲观锁太重了，效率低。

加乐观锁常见的解决方法是用cas自旋。这里我们针对库存不超卖这个问题，进行了改进。
```java
boolean success = seckillVoucherService.update()
            .setSql("stock= stock -1")
            .eq("voucher_id", voucherId).update().gt("stock",0); //where id = ? and stock > 0
```
只用在每次修改库存前进行库存判断：是否库存>0?即可。

## 2.一人一单逐步优化
### 2.1悲观锁解决一人一单问题
很简单的解决思路是：扣库存前，到数据库根据用户id查优惠卷表，看看有没有对应订单。如果有，则返回异常结果，如果没有，则继续扣减库存。
但这同样具有多线程问题。多个线程同时下单，查询数据库发现都没有订单，于是都扣减库存。于是很容易想到用锁来解决。

前面解决优惠卷超卖问题，是修改数据，用乐观锁更高效。但对于插入数据而言，乐观锁难以解决。于是使用悲观锁，在创建订单方法上加个悲观锁。

### 2.2一人一单集群优化
上述加锁方法看似很完美，但如果在集群模式下就失效了。
对于同一个服务器，加的锁是在某个对象，不同线程要拿这个锁，由于是同一个对象，会实现互斥功能。但对于不同的服务器，即使代码相同，不同服务器上的对象天然不同，不同服务器上的不同线程拿到的锁也必然不同，所以无法实现一人一单效果。

于是我们使用分布式锁。
分布式锁实现原理就是不用jvm内部的对象了，使用一个第三方工具：如mysql，redis，zookeeper。由于mysql性能比较低，一般很少人使用。这里我们选用redis。

#### 2.2.1redis实现
我们想到redis setnx这个命令：设置key如果key不存在。如果设置成功，说明加锁成功，如果设置失败，说明加锁失败。
key用用户id，这样，每个用户最多只有一个线程能抢到锁了。

**误删除问题**
但这也有问题，考虑一下问题：
线程1拿到锁后，因为业务阻塞，导致redis key超时释放了。于是线程2拿到了锁，结果线程2还没执行完呢，线程1完成了业务并释放了2的锁（根据key 删除）
解决思路：
思路很简单，我们还没有利用key对应的value呢。存锁时，把对应线程id当value存入，释放锁时，先判断value等不等于当前线程，等于才能删除，不等于则不删。
![[Pasted image 20260605203033.png]]

**原子性问题**
但真解决了吗，我们来看下图情况：
![[Pasted image 20260605203056.png]]
线程1在删除锁前，判断当前锁是自己线程的，结果拿到结果后，阻塞了。然后锁超时释放了。结果线程2拿到了锁，然后在执行业务过程中，线程1结束了阻塞，并把2的锁释放了，这也造成了误删除情况。
解决思路：
造成上述的原因，其实是因为，比较value和删除锁不是原子性的，在他们中间可以插入其他操作。于是我们想到用lua脚本来实现redis操作的原子性。

#### 2.2.2Redission
基于setnx实现的分布式锁存在下面的问题：
- 不可重入：即使是同一线程要进入该线程加锁的临界区，也不能重入
- 不可重试：当前解决方案只能试1次，而不能自旋等待或多尝试几次（虽然可以用个while循环来解决）
- 超时释放时间固定：如果业务处理确实有时需要较长时间，还没处理完锁就释放了，不够合理。
于是我们选用redission来实现分布式锁
- 主从同步不一致：为了提高redis的可用性，我们会搭建集群或者主从，现在以主从为例，此时我们去写命令，写在主机上， 主机会将数据同步给从机，但是假设在主机还没有来得及把数据写入到从机去的时候，此时主机宕机，哨兵会发现主机宕机，并且选举一个slave变成master，而此时新的master中实际上并没有锁信息，此时锁信息就已经丢掉了。

**redission可重入原理：**
它用hash结构来存储数据。key：锁名，field：线程名，value：重入次数。
加锁过程如下（源码实现是一段lua脚本）：
1. 首先判断key 存不存在，如果不存在，则直接设置key：锁名，field：线程名，value：1，并设置过期时间（默认30000毫秒）返回null。
2. 如果存在，接着判断field等不等于当前线程，如果相等，value+1,并将过期时间重新设置（默认为30000毫秒），返回null
3. 如果不存在，则返回这个锁的过期时间。

通过这个value设计，实现了锁的可重入功能

**redission重试机制**
其实是用了一个while true循环来尝试获取锁。

**redission续时机制（看门狗机制）**
在执行完加锁的lua脚本后，会设置一个监听器，即在后台开启了一个线程（看门狗）来进行续约逻辑，这个线程设置一个timeTask，每隔ttl/3的时间就会触发一次timetask来实现续约。然后在续约完成后，新设置一个timetask，从而实现续约的功能。
如果我们的线程宕机了，自然开启的看门狗线程也会宕机，从而没人实现续约功能，而导致锁超时释放。而如果线程没有宕机，看门狗线程会一直存在，从而实现续约功能。

**redission解决主从同步问题**
为了解决这个问题，redission提出来了MutiLock锁，
使用这把锁咱们就不使用主从了，每个节点的地位都是一样的， 这把锁加锁的逻辑需要写入到每一个主丛节点上，
只有所有的服务器都写入成功，此时才是加锁成功，假设现在某个节点挂了，那么他去获得锁的时候，只要有一个节点拿不到，都不能算是加锁成功，就保证了加锁的可靠性。

## 4.从mysql到redis
前面我们在下订单时，无论是查订单数判断一人N单还是查库存防止超卖，都是在数据库内完成的。
但在高并发的情况下，大量的请求 查询数据库和尝试更新数据（update是需要给记录加锁的，存在锁竞争），并且还使用了分布式锁，使得整个秒杀业务的性能受到很大影响。

我使用 JMeter 测试 QPS 1000，200个库存的情况下，平均响应时间是500ms，比较慢，于是我想到用redis缓存来解决订单超卖和一人一单问题。

**防超卖具体实现**
1. 将热门的优惠卷预先缓存到redis里，包括优惠卷个数，活动开始和结束时间（可以用string数据结构）。
2. 那么判断是否超卖时，只用判断库存是否大于0，大于0再将库存-1即可。（同样的，可能存在a检查库存>0后B库存也判断>0，然后A,B都减1的情况，所以使用lua脚本，保证检查和库存-1的原子性）
3. 又因为redis是单线程的，所以不用加锁即可实现防超卖。

**一人一单具体实现**
1. 用set数据结构，存储购买优惠卷的用户id
2. 在判断用户是否购买过时，只用判断用户在不在set中，如果在则直接返回异常结果，如果不在则向set里插入用户id（同样的，为了保证判断和插入的原子性，使用lua脚本）
3. 同样的，因为是redis，所以无需加锁。

**一人N单改进**
1. 将set结构改成hash结构，field存储用户id，value存储购买次数。
2. 判断value是否超过N即可
