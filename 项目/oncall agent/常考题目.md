
# 一.agent架构
## 1.这个项目设计了什么agent
本项目设计了三个agent，分别为知识库agent，对话agent和运维agent。

1. 其中知识库agent用于构建知识数据库。通过自动化流程，将文档变成向量，存入向量数据库中。便于对话agent和运维agent检索。
2. 对话agent采用reAct设计范式，能根据对话查找知识库，并根据返回内容给出相应的回答。同时该agent支持多轮对话和流式对话。
3. 运维agent采用plan-and-execute设计范式，该agent其实是个multi-agent，采用中心化的设计思想，由一个supervisor agent来指挥plan agent和execute agent进行运维分析，通过对log日志的检索和对知识库的查阅，达到快速解决日志报错的效果

### 3.1什么是ReAct agent
ReAct=（Reasoning + Acting）,也就是先思考后行动的agent，具体来说，ReAct 的每一轮循环由三个步骤组成，形成一个完整的 Thought -> Action -> Observation 循环。

Thought 阶段，LLM 先把当前的情况分析一遍，把推理过程写出来，比如「用户想查竞品信息，我应该先用搜索工具查一下竞品 A 的最新动态」；
Action 阶段，LLM 根据思考的结论决定调用哪个工具、传什么参数；
Observation 阶段，工具返回的结果被反馈给 LLM，它读取这个结果，

### 3.2什么是Plan-Execute
在做出行动前，先由一个agent专门做规划，输出一个完整的步骤列表。再由另一个agent逐步执行。同时这个计划并不是固定死的。可以再让一个agent 分析结果，或再让plan agent分析结果，重新生成计划或结束循环。

### 3.3区别，为什么对话agent用reAct而运维agent用plan-and-execute
 reAct是「走一步看一步」的模式，每一步都是局部最优决策，处理特别复杂的、需要全局规划的任务时，容易在中间迷失方向。
 plan-and-execute刚好解决了这个问题，它先拆解步骤，再执行，根据执行结果判断要不要修改计划。
在这个项目里，对话agent处理的是用户提的问题，比如问怎么调用某个api，这类问题执行步骤不会很长，适合使用reAct设计范式。
而运维agent专门处理日志报警问题，目标清晰且执行步骤相对较多（比如查日志，分析日志，怎么解决等）适合使用plan-and-execute设计范式。

## 4.你是怎么设计Prompt的？
对于每个agent，我会分三个部分设计它的prompt
第一部分，角色：比如对话agent，我会在prompt写你是对话助手。运维agent，我会在prompt写你是一个运维助手。
第二部分，核心功能：我会在这部分告诉ai你要使用的工具和要做的事。
- 对于对话agent，因为用户提问一般比较多元，所以我会在prompt写根据用户问题，尝试调用知识库或联网查询。
- 对于运维agent,因为这方面目标比较清晰，所以我会将常见的运维思路作为例子告诉agent该怎么做，如先调用查日志工具看日志，然后查知识库找解决方案，然后将问题和解决方案汇总。
第三部分，输出：我会告诉agent最终输出要纯文本，对于运维agent可以规定输出格式为：日志现象：xxx,推测问题：xxx，解决方案：xxx。

# 三.RAG
[[agent#五.RAG]]
## 1.简单介绍一下RAG
RAG（Retrieval-Argumented Generation）顾名思义，就是通过检索增强生成。在大模型回答用户提问之前，先搜索知识库，再根据检索到的文档，结合用户问题，回答出更符合知识库的内容。

## 3.你的文档是怎么分块的？检索TopK参数是怎么确定的？
**对于文档是怎么分块是这样的：**
我了解到有一下几种分块策略
- 按固定大小切分
- 按语义切分
- 父子切分
固定大小切分就按固定的大小切分文档。语义就是按标题，段落切分。父子切分就是一份文档存两份，一份小一点比如200token，一份大一点比如800token，查找时用小的查，比配到相似的返回大的那一份给模型。
本项目采用的是按语义来切分。主要原因是，
采用固定大小分块，容易将一句话拆成两个向量，不够精确。并且实验的文档大多是markdown格式，标题划分清晰。采用语义划分已经足够精确，且比父子划分更简单。

具体划分过程是，先将文档按标题划分，然后再对每个标题内的内容，根据段落，如换行等进行划分。每一个chunk保证>300字符，<800字符。除非一个标题内的内容非常少或划分到最后一个段时剩下的内容很少，我就会将其与上一个chunk合并起来。并且我还对其进行了重叠优化：也就是前后各重叠100token，以防止将同个意思但分散在两个段落的句子拆开。

**对于TopK是怎么选的？**
首先TopK的意思是召回前k个相关的chunk。如果topk太小，容易丢失真正相关的chunk。如果topk太大一方面是对于token的消耗过大，另一方面是占用过多上下文，造成lost in the middle现象。
本项目中，我选用的TopK的值为3，我是这么考虑的：
第一，本项目中我采用的是双路召回模式。根据向量检索，BM25分别召回top20的chunk，接着再rerank选出top3，这样先初筛后精晒筛的方式选出的已经足够准确。
第二，本项目的数据库其实并不算太大，所以选用Top3已经足够适用。或许以后面对更大知识库的情况下我会进行调整。

**并且，我也对精确度进行了实验：**
评判标准分两点：
- chunk有没有被检索出来，
- 最精准的chunk排名在第几位。
我是这样评估的，一开始，我先根据文档某块内容，向提问agent提相关问题，并在召回的topK里评判。后来我发现太麻烦了，设计了一个agent专门用来评估，让他模仿我前面的行为来评测，最好测出精确度大约在85%。

## 5.了解RAG范式吗？
[[agent#3.RAG范式]]
本项目用的是self RAG即Agentic RAG，它与传统RAG不同之处在于，调用数据库并不固定在agent回答之前，而是作为一个工具供agent使用。对于一些简单问题，比如：hello，我是谁？完全不用调数据库，agent就能直接返回。

## 6.在RAG知识库系统中，如果用户查询的意图与已有文档语义不匹配，导致检索准确率下降，你会如何设计一个反馈闭环来持续优化检索效果？

我会从三个层面设计：
第一个层面在检索层：我设计了如果向量匹配度低于0.7,将直接返回空文档，给用户返回当前知识库里没有相关知识，并将对应提问记录在日志里，根据问题添加相关问题。
第二层面在线上：我设计了用户可以对agent回复问题点踩，并可以进行追问。这些点踩和追问的问题将被记录，用以判断是语义不匹配还是回复不相关。
第三层是优化：对于前面收集到的提问到达一定数目后，进行优化，先进行query改写，进行搜索后，再次判断相关度。判断是用户的提问不准确还是知识库没有。如果是提问不匹配，对query优化进行改进，如果是知识库没有则选择知识库扩充。


# 四.对话功能
## 1.你是怎么实现多轮对话的，并实现用户隔离的？
使用concurrenthashmap，存储用户id以及对应session，session里存储一个List，该List每一个数据是一个Map，key是角色，value是回答。对于用户隔离，是根据用户id取session，该session里记录有用户前面的对话记录。在下一次对话前，把对话记录添加到问题前，即可实现多轮对话和用户隔离。
