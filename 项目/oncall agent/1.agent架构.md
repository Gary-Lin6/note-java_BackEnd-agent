
# 一.介绍一下设计的agent架构
本项目设计了三个agent，分别为知识库agent，对话agent和运维agent。

1. 其中知识库agent用于构建知识数据库。通过自动化流程，将文档变成向量，存入向量数据库中。便于对话agent和运维agent检索。
2. 对话agent采用reAct设计范式，能根据对话查找知识库，并根据返回内容给出相应的回答。同时该agent支持多轮对话和流式对话。
3. 运维agent采用plan-and-execute设计范式，该agent其实是个multi-agent，采用中心化的设计思想，由一个supervisor agent来指挥plan agent和execute agent进行运维分析，通过对log日志的检索和对知识库的查阅，达到快速解决日志报错的效果。

## 1.什么是ReAct agent
ReAct=（Reasoning + Acting）,也就是先思考后行动的agent，具体来说，ReAct 的每一轮循环由三个步骤组成，形成一个完整的 Thought -> Action -> Observation 循环。

Thought 阶段，LLM 先把当前的情况分析一遍，把推理过程写出来，比如「用户想查竞品信息，我应该先用搜索工具查一下竞品 A 的最新动态」；
Action 阶段，LLM 根据思考的结论决定调用哪个工具、传什么参数；

## 2.什么是Plan-Execute
在做出行动前，先由一个agent专门做规划，输出一个完整的步骤列表。再由另一个agent逐步执行。同时这个计划并不是固定死的。可以再让一个agent 分析结果，或再让plan agent分析结果，重新生成计划或结束循环。

## 3.区别，为什么对话agent用reAct而运维agent用plan-and-execute
 reAct是「走一步看一步」的模式，每一步都是局部最优决策，处理特别复杂的、需要全局规划的任务时，容易在中间迷失方向。
 plan-and-execute刚好解决了这个问题，它先拆解步骤，再执行，根据执行结果判断要不要修改计划。
在这个项目里，对话agent处理的是用户提的问题，比如问怎么调用某个api，这类问题执行步骤不会很长，适合使用reAct设计范式。
而运维agent专门处理日志报警问题，目标清晰且执行步骤相对较多（比如查日志，分析日志，怎么解决等）适合使用plan-and-execute设计范式。

# 三.Tool

## 1.该agent设计了什么tool？
其实tool就是agent要有的能力嘛，对于这个项目，
- 很明显需要查知识库，所以我设计了一个查询知识库的tool，它能返回tokK个相关片段给agent
- 其次运维agent需要查询日志，其中一个tool就是列出当前有什么日志。同时我还了解到腾讯云cls mcp可以实现自然语言日志检索。
- 除了查日志外，我还了解到Prometheus这个告警查询工具，它可以直接获取当前活跃告警信息
- 同时在检测时我发现，agent不知道此时的时间，如果用户询问有关时间的问题很容易出错，所以我写了个工具用于返回当前时间。
- 最好我发现用户在查询知识库外的知识时容易出错，所以我实现了个联网查询工具，用于查询相关信息作为兜底方案。
